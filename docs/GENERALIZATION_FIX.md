# 泛化修复：把「表面形式 → 动作」的捷径打断

R4.5 的分布外读数证明了一件对项目不利的事：拿到 GO 的候选在模板外只有 **0.5833**，
表达变化一类 **0/20**，**比零训练基座还差**（[`OOD_EVALUATION.md`](./OOD_EVALUATION.md)）。

2026-08-16 的外部审阅把这件事顶到了天花板上：

> 8.5 到 10 的差距不在工程，在**有一个扛得住分布漂移的结果**。

这份文件是那个结果。**它同时包含一个必须一起说的代价。**

- 日期：2026-08-17
- 机器：gpu-5090，物理 GPU 0
- 关联：ADR 0005（评测集按哈希切分）、LOG-20260816-01（v1 的读数）

---

## 1. 诊断（先做这一步，不是先猜修法）

把 v1 的 `expression_ood` 按子类拆开：

| 子类 | 零训练基座 | 拿到 GO 的候选 |
|---|---|---|
| `code_switch` | **1.0** | **0.0** |
| `colloquial` | **0.5** | **0.0** |
| `typo` / `terse` / `greeting_noise` | 0.0 | 0.0 |

**训练把基座本来会做的两类打没了**，20 条失败**全部**是 `premature_final_response`
——正是 R3 那个「说完就停」。

**机制**：240 条训练数据全部来自 `formal_tasks._user_request` 的 **12 句模板**，
且 12 句**全部**是「请核实 / 请检查 / 请查询…」的书面祈使句。模型学到的是
**表面形式 → 动作**的触发器，不是**语义 → 动作**。换一种说法触发器不响，
模型就退回用自然语言解释。

## 2. 干预：只改「顾客怎么说」，不改「Agent 该做什么」

用 DeepSeek 生成 **267 条**顾客原话（40 次请求，**$0.0061**），经两道校验：

1. **结构校验**：恰好一个 `{order_id}` 占位符、长度在区间内、不含工具名，
   且**不得透露订单状态**（「已经过期了」「不是我的单」——顾客一旦说破，
   Agent 不查订单也能猜对，任务就从「查证后判断」退化成「读理解」）；
2. **语义回环校验**：把措辞反过来让模型分类回意图，不一致即丢弃。

**一个必须记下来的设计错误**：第一版按「场景」写生成简报，写出了
「顾客要退款，但自己也提到时间已经过去挺久了」这种 brief。回去核对冻结契约才发现
四个退款场景的请求模板**语义完全相同**，区别全在**订单状态**里，顾客的话一个字都没提。
按场景写等于把答案写进用户的话。已改成按**意图**（三类）生成。

措辞池按 `sha256(措辞 + 固定盐)` **确定性三分**：
`train_aug` 147 / `ood_dev` 59 / `ood_sealed` 61。分片不看场景、不看风格、不看顺序
——由人挑就没有任何东西能阻止「把好改的留给评测」（ADR 0005）。

训练侧：每条任务额外产出 3 条**只改写 user 第一句话**的样本，assistant 的工具调用、
tool 观测与 `target_state` 一个字不动。sft 行数 400 → 1600，
去订单号后的不同说法 **42 → 184 种**。

## 3. 评测集：OOD v2

六个冻结场景 × 每场景 10 条 = 60，业务语义与 `_scenario_contract` 逐条对应，
**唯一自变量是 user 的第一句话**。`ood_dev` 用于迭代，`ood_sealed` **只观测一次**。

**为什么必须覆盖六个场景**：只在 `refund_eligible` 上修和测，最省事的「修法」是
让模型见谁都退款——那会在四个拒绝类上崩掉，而单场景的评测集看不见。

**oracle 可解性已验证**：gold 调用序列在环境里跑一遍，两个分片各 60/60 到达
`target_state` 且零政策违规。这一条不过，整份评测测的就是真值写错了。

### 3.1 分离是**经验证实的**，不只是构造上应该如此

「分片互斥」有两个强度：一是「导出流水线**应该**保证互斥」，二是「实际写进
`sft.jsonl` 的那些句子里，**确实**没有一句是评测集用的」。后者不信任任何中间环节，
直接读产物比对。实测：

| | 措辞条数 | 其中确实出现在真实训练文件里的 |
|---|---|---|
| `train_aug` | 147 | **142** |
| `ood_sealed` | 61 | **0** |

（`train_aug` 有 5 条没被取到，是因为每条任务只从池子里取 3 条，属正常。）

这条由 `tests/test_ood_v2_tasks.py::test_no_evaluation_phrasing_appears_in_the_actual_training_file`
锁定——它读 `train-export-007/sft.jsonl`，把订单号归一化后逐句比对。
**早期版本的互斥测试只取了 `train_aug` 里一个意图**（`refund_request`），
另外两个意图的重叠会漏检；已改为取全部意图，并补上这条直接读训练文件的更强断言。

**新候选把三个拒绝类全部保持在 1.00**。这一条比总分更重要：它证明修法**不是**退化成

### 合并/未合并的混淆已排除

`sft-006` 此前的 OOD 读数走的是合并权重，新候选走 base + adapter。为去掉这个可被质疑的点，
额外跑了 `sft-006` 的**未合并**形态：0.7333 vs 合并版 0.7167，逐类别几乎相同
（recovery 0.5 vs 0.4）。结论不依赖加载方式。

## 5. 代价：dev 上多了 2 次政策违规

**这不是脚注，是这次干预的账单。**

| 候选 | dev 60 | 政策违规 | 失败签名 |
|---|---|---|---|
| `sft-006` | 58–60/60（三次运行） | **0** | `recovery_failure` |
| `sft-007` | 58/60 | **2** | `refund_denied_window` / `refund_not_eligible` |
| `sft-008` | 58/60 | **2** | **完全相同的签名** |

两个只差 oversample 的候选出现**完全相同**的失败签名，因此这 2 次违规
**不是 oversample 造成的，是措辞增强本身的代价**：更多「用户开口要退款」的说法
让模型更倾向执行，而四个退款场景的请求在语义上**本来就无法区分**——
区别全在订单状态里。

**严重性口径**：`policy_violation` 是安全类失败，比同量级的任务失败更严重。
`sft-006` 在 dev 上是 0。**这一条必须与 OOD 的收益一起引用。**

一个尚未解释的现象：同一类别在 `ood_dev` 上是 **1.00**（10/10 全对），
只在模板内的 dev 上失败 2 条。n=10，也可能只是噪声，**没有进一步验证，不做解释**。

## 6. 候选选择：规则事先写定，且规则本身被证伪了一半

选择规则在看到 `sft-008` 任何读数**之前**写进 `task_plan.md` 并提交
（commit `3416cee`）。原假设是「去掉 oversample 会消掉那 2 次违规」——**被证伪**。

规则第 3 条原文是「假设被证伪 → 选 `sft-007`（**OOD 更好**）」。括号里那句是写规则时的
预期，而实测 `sft-008` 的 OOD **更好**、dev **完全相同**。按字面执行会选中一个被严格
支配的候选。**因此选了 `sft-008`，并把这次偏离字面规则的事实与理由写进了 `task_plan.md`。**

教训：别在规则里塞入对结果的预期，那会让规则在预期落空时自相矛盾。

### 7.2 又一个满分，所以先说它为什么可能

60/60 是本项目第三个满分，按 [`READING_THE_NUMBERS.md`](./READING_THE_NUMBERS.md)
的规矩，它必须自带解释：

**这个集合的业务逻辑与训练数据完全相同**——同样六个场景、同样的状态判定、
同样的 verifier，**唯一的自变量是顾客怎么说**。一个真正学到「语义 → 动作」的模型
在这里接近天花板是**应该**的；`sft-006` 拿到 0.7333 恰恰说明它没学到那个映射。

所以这个 1.0000 支持的结论**只有一句**：模型不再依赖那 12 句模板的表面形式。
它**不支持**「模型能处理没见过的业务场景」——那要看下面 §7.3 的迁移检查，
而那里它掉到了 0.8667，并且有一类明确变差了。

**这是本轮最有说服力的一组**：v1 由作者手写、生成过程与 v2 毫无关系、
本轮**从未用于任何选择**。`expression_ood` 从 **0.00 涨到 1.00**，
五个子类（`code_switch` / `colloquial` / `greeting_noise` / `terse` / `typo`）**全部 1.00**。

**但它同时暴露了代价的第二个面**：`scenario_ood` 从 0.75 **掉到 0.60**，

收益（该动手时动手）与代价（不该动手时也动手）来自同一个改动，**不能只报一半**。

（非法调用 44 → 38 → 23：新候选也更好，但**不为零**——v1 含脏字段与工具诱导，
这一类本来就不该期待清零。）


## 8. 明确不声称

- **不是「泛化了」**，是「对**同一个生成器**产出的、训练从未见过的措辞更鲁棒了」。
  措辞池由单一 provider、单一 prompt 生成；对任意真实用户输入的鲁棒性**没有被测量**。
- **不是发布判定**。封存 120 条 holdout 本轮**没有观测**，四次观测的结论一条未改。
  拿 `sft-008` 去跑那个集合会是**第五次**观测。
- **自变量不纯**：sft 行数 400 → 1600，同样 3 epoch 下梯度步数 75 → ~300。
  本轮改的不只是「说法更多样」，也包括「训练更久」，两者在这个设计里分不开。
- **n = 60，逐场景 n = 10**，逐类别 CI 宽度约 ±30pp。足以看方向，**不足以排序**。
- **v1 那 60 条本轮不用于任何选择**，只作独立迁移检查（ADR 0005）。
