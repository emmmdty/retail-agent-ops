# 面试材料

取数口径以 [`RESUME_EVIDENCE.md`](./RESUME_EVIDENCE.md) 为准，观测次数以
[`HOLDOUT_LEDGER.md`](./HOLDOUT_LEDGER.md) 为准。本文件不新增任何数字，只组织表达。

三条纪律：**不说没运行过的数**、**不把内部固定子集说成公开榜单**、
**不把单次演示说成生产稳定性**。

## 1. 五分钟讲解（约 750 字，按段落计时）

### 0:00–0:40 是什么

我做了一条零售工具 Agent 的**领域适配与发布流水线**。场景很窄：订单查询和退款，
两个业务工具、六类任务、全中文。窄是故意的——我想验证的不是"Agent 能做多少事"，
而是"把一个小模型调到能在这个场景上线，中间需要哪些工程环节，以及怎么知道它真的行"。

链路是四个命令：`build`（造轨迹并做执行式质检）→ `evaluate`（在冻结任务上配对评测）
→ `release`（按门禁出 GO/NO-GO）→ `serve`（只加载通过门禁的权重）。
全部跑在一张消费级显卡上。

### 0:40–1:40 最难的部分不是训练，是"怎么知道结果可信"

Agent 评测最容易骗自己的地方是：用文本相似度当成功率。我的主判据是**工具执行后的
最终状态**加**政策 verifier**——退款到底有没有发生、有没有违反业务规则。

为了让两次运行可比，配对比较前会强制校验模型 revision、生成参数、数据集版本、
代码 commit、依赖锁、system prompt 哈希**逐字段相同**，任何一项不同就拒绝配对。
运行报告的 ID 是它自己全部字段的哈希，改一个字节就对不上。

120 条 holdout 是**封存**的：两段式授权门，整个开发期只被观测了四次，每次都对应
一次正式发布判定，结果不许反馈进开发。

### 1:40–3:00 结论一：我把提示词和后训练的功劳分开了

大多数微调项目会说"微调后提升了 X"。我做了一个 2×3 配对实验：
2 种 prompt × 3 档 LoRA 容量（零训练 / 只挂 attention / 全 linear），六次运行、每格 60 条冻结任务。

结果是**两者修的是不同的失败，几乎不重叠**：一句显式授权指令，让"判定可退却不敢
执行"这类从 5/10 涨到 9/10，而"工具失败后重试"这类**零变化**；后训练则把重试类
5/10 打到 10/10。

这件事的价值是：我原本可以写"候选比基座高 20 个点"。是我自己去测了"给基座也换上
那句提示词"，才发现那 20 个点里有一半是免费的。**如果不做那次对照，那个数字放到
简历上就是虚的**，面试官只要问一句"你的基座用什么提示词"就会露。

### 3:00–4:00 结论二：LoRA 容量必须和模型规模匹配

4B 上只挂 attention 投影时，微调对目标能力是**负作用**；加上 MLP 三个投影，
同一份数据、同一组超参，从负作用变成满分。我本来打算把这写成"容量决定训练效果的
符号"。

然后我去 1.7B 上复现——**方向反了**。1.7B 上 attention-only 是强正作用，
全 linear 反而几乎无增益，而且 15 条失败全部是"该拒绝却没拒绝"，是**学过头**：
容量过剩被训练数据 2:1 的执行偏向带跑，拒绝能力从 30/30 掉到 15/30。

所以真正的规律是容量得跟规模匹配，而且**数据配比和容量是耦合的，不能当成两个独立
旋钮**。这条是我自己的实验推翻我自己上一条结论得来的。

### 4:00–5:00 结论三：一个 GO，和它旁边必须一起说的东西

前三次判定都是 NO-GO。第三次最难受：候选在 120 条封存任务上做到 **120/120**、
成功率 +14.2 个点、政策违规和非法调用全部清零——但 p95 延迟比值 1.88，超过 1.25 的
门禁上限，被拒。**我没有改阈值**，有测试锁定它逐字段不变。

然后我去归因，发现慢的原因**不是"它多做了工具调用"**（次数只多 14.6%），而是
**单次调用耗时翻倍**——全 linear LoRA 每次前向多做七次低秩矩阵乘。于是我把 adapter
**合并回基座权重**，同一份权重、同一套行为、调用次数一模一样，p95 比值降到 1.13，
拿到项目历史上第一个自动门禁 **GO**。

但这个 GO 旁边必须放另一个数：我又建了一个**分布外**任务集，同一个候选掉到
**0.5833**，其中"换个说法"这一类是 **0/20**，比零训练基座还差。
**120/120 不是泛化**——冻结 holdout 和训练集共用同一批请求模板。这次微调其实是
**用表面形式的鲁棒性，换来了任务结构与安全性**。

我认为这条自己打自己的证据，比那个 GO 更值钱。

**但故事没停在这里。** 我把机制诊断出来了：240 条训练数据的请求全来自 12 句模板，
而且 12 句**全是**"请核实 / 请检查"的书面祈使句。模型学到的是**表面形式 → 动作**，
不是**语义 → 动作**——换种说法，触发器不响，它就退回用自然语言解释。

于是我用 LLM 生成了一个措辞池做训练增强，**只改用户的第一句话**，工具调用和目标状态
一个字不动。措辞按哈希确定性三分，训练用的和评测用的**逐条互斥**，并且留了一个
**只观测一次**的分片。结果：那个分片上从 0.73 到 **满分**；在一个我**从未用来选候选**的
独立集合上，"换个说法"那一类从 **0.00 涨到 1.00**。

**后来我又生成了第二份措辞池**，因为一份素材上的满分分不清"模型鲁棒"和"那批说法恰好
好做"。同一份权重在第二份上是 **0.9833**，不是满分。所以我现在的说法是
"**两份独立措辞池上分别 1.0000 与 0.9833**"。

**代价我也量出来了**：模型变得更倾向执行，于是"不该动手时也动手"——封存 120 条上
**同一份配置的两次训练分别有 2 次和 7 次政策违规**，全部是"给已过退款期限的订单退款"；
"做不到的请求"那一类从 0.75 掉到 0.60。**收益和代价来自同一个改动。**

**而且这笔账我一开始记小了。** 我原本说那 2 次违规是"措辞增强的确定代价"，
论据是两个只差一个开关的候选失败签名完全相同——**但它们共用一个训练 seed**。
换 seed 重建之后，dev 上零违规、封存 120 条上 7 次。**我的复验没有确认我的结论，
而是推翻了我自己写的一条归因。** 这一段我在面试里会主动讲。

## 2. 深挖问答

### 2.1 系统设计

**Q：为什么不用 LangChain / LlamaIndex / 现成 Agent 框架？**
A：这个项目的复杂度不在编排，在**证据链**。Agent 本体就是一个最多 5 步的 ReAct 循环，
三个工具，正则解析——用框架也是这几十行。而框架给不了我需要的东西：运行报告全字段
自哈希、配对比较前的逐字段同条件校验、封存 holdout 的两段式授权、发布门禁的版本化。
我需要精确控制"什么条件下两次运行可比"，框架的抽象层反而会挡住这件事。
反过来说，如果需求是"接二十个工具、多 Agent 协作"，我会用框架，那时复杂度在别处。

**Q：为什么不直接用 GPT-4 / Claude，非要微调一个 4B？**
A：目标场景是**企业内网、成本敏感**。商业 API 在这个项目里我用了——作为 **teacher**
采集轨迹，两批合计 1045 次请求、约 $0.111（第一批 519 次 / $0.055 暴露了一个环境缺陷，
修完后第二批 526 次 / $0.0559 才是训练数据的来源）。但部署侧要的是数据不出内网、单卡能跑、延迟可控。
所以问题不是"哪个模型更强"，而是"4B 能不能在这个窄场景上做到可上线，以及怎么证明"。
顺带说，我并没有拿到"可以上线"——SPEC 的第六条门禁我做完了独立重建复验，
但仍然只在一个窄到不能再窄的场景上成立。

**Q：`build/evaluate/release/serve` 这四个接口是怎么定下来的？**
A：按**产物的不可逆性**切的。`build` 产出的是数据，可以重造；`evaluate` 产出的是
证据，一旦产生就不许覆盖（输出目录是不可覆盖语义）；`release` 产出的是判定，
它引用两侧证据的哈希；`serve` 只消费判定。这个方向是单向的，所以依赖方向也强制
单向：`product_cli → retail_ops.* → core.*`，有治理测试锁定。

**Q：guardrail 为什么不做成环境的一个方法？**
A：那样两层就退化成一层。环境校验管的是"这个调用在业务上合不合法"，guardrail 管的是
"这个调用该不该发生、这个工具返回的内容能不能进模型上下文"。间接 prompt injection
是从工具**观测**进来的，环境自己不会觉得有问题。分层的代价是多一次遍历，
收益是任一层被绕过还有另一层。

### 2.2 评测方法

**Q：120 条 holdout，n 是不是太小？**
A：太小。每类 20 条，`ci95` 在满分时是 [1.0, 1.0] 的退化区间，那不是显著性证据。
我在文档里明确写了不可写的表述清单，"120/120 证明模型可靠"是其中一条。
n 小是数据成本的直接后果——每条轨迹要过 replay、最终状态、政策 verifier 三重校验。
如果要扩，我会先扩**分布外**集合而不是同模板的 holdout，因为后者已经被证明测不出泛化。

**Q：你怎么防止 holdout 泄漏？**
A：三层。第一层，train/dev/holdout 的 ID 和五维指纹互斥，加载时交叉断言；
第二层，两段式授权门——没有显式授权，读取封存数据的路径直接抛错；
第三层，公开产物是 allowlist 字段集，有泄漏扫描测试，`scripts/ci/audit_public_release.py`
还会扫全部被跟踪文件。另外整个开发期我只观测了四次，每次都记在台账里。

**Q：`verifier_reward` 为什么不是主判据？**
A：因为它**四次**与主判据反向。最典型的一次：候选的 `verifier_reward` 从 0.5646
升到 0.7500，而任务成功率下降了。复合奖励里的格式分量会掩盖执行能力退化。
这是我坚持"最终状态与政策 verifier 是唯一主判据"的实测依据，不是信仰。
现在它在报告里被降级为诊断量，和主指标分开呈现。

**Q：p95 延迟这种指标跨运行可比吗？**
A：不可比，而且我在文档里明说了。GPU 是共享的，不同运行他人占用 0%–98% 不等。
所以门禁用的是**同一次运行里 base 与 candidate 的比值**，不是绝对值。
即便如此，base 侧 p95 在第二次和第三次观测之间仍有 9% 的波动——合并形态的门禁余量
只有 1–3%，我因此不表述为"延迟问题已解决"。

### 2.3 后训练

**Q：为什么是 SFT 不是 DPO / RL？**
A：预设的进入条件是"稳定错误类别能构造足量执行有效的偏好对，且 SFT 已停滞"。
SFT 没有停滞——第二轮的容量变量一改就从负作用变成满分。而且我的失败根因分析显示，
问题是**条件决策**（什么时候该执行、什么时候该拒绝），不是排序问题。
在这个规模上加偏好优化更像是为了让简历有算法叙事。

**Q：你的训练数据是模型生成的，怎么保证质量？**
A：不看文本看**执行**。每条 teacher 轨迹都要能 replay、最终状态要正确、要通过政策
verifier，三重校验后通过率 238/240。而且我发现过一个只有真实 API 采集才暴露的
环境缺陷：`refund_denied_window` 这类任务的判定依据 `current_day` 从来没暴露给模型，
任何推理式 Agent 都无解——CPU 测试全走 Oracle 所以发现不了，真实采集通过率只有 30%
才暴露出来，修完 95%。

**Q：LoRA 的超参你调了吗？**
A：**没有系统调参**，这是有意的。r=16 / alpha=32 / lr=2e-4 / 3 epoch 全程固定，
每轮只动一个变量。原因是单 seed 开发下，调参和变量效应会混在一起，而我要的是
"这个变量有没有效应"的干净读数，不是最优点。代价是我不知道最优超参在哪里，
这一点我不会假装知道。

**Q：只跑一个 seed，结论稳吗？**
A：这是真实局限。我做了一次**独立重建复验**（SPEC §6 第 6 条）：同一份配置换训练
seed 从头重训，看结论是否保持。过程中发现一件事——**同 seed 重跑也拿不到逐位相同的
adapter**，所以"重建"在这个栈上只能是分布意义上的，不是复制。具体读数见
[`REBUILD_VERIFICATION.md`](./REBUILD_VERIFICATION.md)。

### 2.4 工程决策

**Q：门禁阈值是你自己定的，那不是想过就能过？**
A：所以有两条硬约束。第一，阈值在看到任何候选读数**之前**定稿，且有三层锁：
`test_thresholds_come_from_the_untouched_release_yaml` 钉住 `release.yaml` 的字面值与键集合；
`invalid_call_count_max` 的类型就是 `Literal[0]`；而 `release.yaml` 本身是 `bundle_sha256`
的哈希分量——**改一个阈值会让磁盘上每一份已有 sealed 证据配对失败**，这比测试更难绕过。
（顺带说：我一度在台账里引用错了测试名，是一次外部审阅抓出来的——那个测试比较的是两份
不含阈值的配置文件。结论没错，引用错了，已更正。）
第二，前三次判定都是 NO-GO，我一次都没改。
最难的是第三次：候选 120/120、成功率 +14.2 个点，只输在延迟。那时候改一个数字就
"成功"了，我改的是部署形态。

**Q：为什么发布门禁要"版本化"而不是直接改？**
A：`GATE_IDS` 是磁盘上全部已有 release 报告的加载契约。就地增删会让此前所有 GO/NO-GO
报告无法加载——那是不可逆的证据损失。所以新口径走 v1.1 新集合，v1.0 逐字节冻结，
两套并存。同样的道理适用于封存证据契约：为了让"合并部署形态"能进配对判定，
我把它版本化到 v1.1，并验证了七份旧证据的 `report_id` 复算**逐位不变**。

**Q：你怎么保证"证据说的运行环境"就是真的运行环境？**
A：一开始不能保证，这是我自己发现的一个洞。`uv_lock_sha256` 哈希的是仓库里的
`uv.lock` **文件**，不是实际装了什么包——我拿一个完全不同的 venv（Python 3.12 + vLLM）
跑评测，产出的证据仍然逐字段声称用的是冻结依赖，没有任何机制发现得了。
修法是新增 `inference_engine` 和 `runtime_env_sha256` 两个字段，按解释器的
purelib/platlib 扫描而不是沿 `sys.path`（第一版就是这么写的，结果同一个 venv 里
两次评测记下不同摘要，那个字段成了噪声，比没有更糟）。关键约束是**不能改变已有 48 份
证据的哈希**，所以用"新字段取值为 None 时不入哈希"而不是版本化投影。

### 2.5 失败与边界

**Q：这个项目最大的局限是什么？**
A：领域太窄，而且我有实测证据说明这有多要命——冻结 holdout 上 120/120 的候选，
换一批**说法不同**的请求就掉到 0.58，表达变化那一类是 0/20，比不训练还差。
换句话说这次微调学到的很大一部分是"这种措辞出现时该退款"，不是"什么时候该退款"。
如果要产品化，第一件事是把评测集从模板内插值改成真实分布采样，而不是继续调模型。

**Q：如果给你多一个月，你会做什么？**
A：三件事，按优先级。第一，把分布外集合做成**门禁的一部分**——但那要先解决
"OOD 集合会不会被过拟合"，需要一个不封存的开发集和一个封存的 OOD holdout。
第二，验证"去掉 4-bit 量化能否直接过延迟门禁"——我已经量出来去掉 NF4 是 1.64 倍
提速、且不需要任何新依赖，但验证它等于消耗第五次 holdout 观测，需要单独决策。
第三，把工具面从 3 个扩到 15 个以上，看现在这套结论有多少能撑住。

| 6 | 把 4B 的结论当成了一般规律 | 去 1.7B 上复现，**方向相反** | 结论改写为"容量必须与规模匹配"，历史条目不改写、以最新条目为准 |
| 7 | 证据声称的运行环境是假的 | 用完全不同的 venv 跑评测，证据仍声称冻结依赖 | 新增两个运行环境字段；第一版实现用 `sys.path` 扫描，同一 venv 两次记下不同摘要，改为按解释器扫描 |
| 8 | 外部 API 有重试分类但**没有超时** | R5 故障矩阵逐条对照 SPEC §9 时发现：超时被归类为可重试，但 SDK client 从未设置超时，落到默认 600 s | 显式 60 s 超时 + 分层重试上限，两层乘积可预测 |
| 9 | **我自己写的评测数据生成 brief 把答案写进了用户的话** | dry-run 时看到生成的措辞里，「窗口过期」和「不是本人」两个场景的限定条件互相串了。回去核对冻结契约才发现：四个退款场景的请求模板**语义完全相同**，区别全在订单状态里，顾客一个字都没提 | 改成按**意图**（3 类）而不是按场景生成，并把「不得透露订单状态」做成硬过滤。按场景写等于让 Agent 不查订单也能猜对，任务从「查证后判断」退化成「读理解」 |
| 10 | **我写的候选选择规则里塞了对结果的预期** | 规则第 3 条写「假设被证伪 → 选 sft-007（OOD 更好）」，实测反过来：sft-008 的 OOD 更好、dev 完全相同。按字面执行会选中一个被严格支配的候选 | 按实质择优，并把偏离字面规则的事实与理由写进 task_plan。**别在规则里塞对结果的预期** |
| 11 | 一个第二个 Python 环境搞崩了整个项目 | 引入 vLLM（Python 3.12）后，项目自己的 HF 评测路径全线崩溃，错误信息（"找不到 C 编译器"）完全不指向真正原因 | triton 的 `cuda_utils` 缓存键不含 Python ABI，两个 venv 互相覆盖。修法是给第二个环境独立的 `TRITON_CACHE_DIR`，并写进资源约束 |

## 4. 常见质疑与回应

| 质疑 | 回应 |
|---|---|
| "结果是不是挑出来的？" | 每次改动前写定收益门槛与停止条件，判负就停。第一轮改进达不到门槛就按预设停止条件停了，没有继续调到好看为止 |
| "门禁是你自己定的" | 阈值在看到读数前定稿，有测试锁定逐字段不变；前三次判定都是 NO-GO |
| "120/120 是不是过拟合了？" | 是。而且是**我自己**建了分布外集合把它测出来的：同一候选 0.5833，表达变化类 0/20 |
| "CI 通过了吗？" | **没有**。仓库当前没有 remote，workflow 已提交但从未真正运行过——文档里明写了这一点，本地等价命令逐条列在 workflow 注释里 |
| "为什么包名和产品名不一致？" | 历史原因（原 VeriTool-RL），全仓重命名需要独立计划。分发名与 CLI 是 `retail-agent-ops`，Python 导入名仍是 `veritool_rl`，边界写在 `REPO_MAP.md` |
| "这跟 BFCL 成绩什么关系？" | 没关系。BFCL 是 legacy 轨道的外部回归，163/200 与 167/200 是**项目自划的固定单轮 AST 子集**，差值置信区间跨 0，不是公开榜单成绩也不能声称稳定提升 |

## 5. 开场自我介绍（30 秒版）

> 我做了一条零售工具 Agent 的单卡适配与发布流水线。最有意思的结论不是模型变好了多少，
> 而是我用一组配对实验把"提示词工程"和"后训练"的功劳分开了——一句提示词就解决了
> 大半的"不敢执行"，而"失败后重试"只能靠训练。最终候选在封存测试集上做到 120/120，
> 拿到了自动门禁 GO；但我又自己建了一个分布外集合，把这个 GO 打掉了一半——
> 同一个候选在换了说法的请求上只有 0.58。**我认为能拿出推翻自己结果的证据，
> 比拿出一个没人敢信的提升更有价值。**
