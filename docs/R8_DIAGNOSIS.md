# R8 阶段性诊断：为什么效果不好

**日期**：2026-08-21
**作者**：opencode（基于项目实测数据 + 外部文献）
**目的**：定位模型效果不佳的根因，区分数据、方法、工程三个维度，为后续改进提供依据。

---

## 一、现状摘要

| 指标 | 值 | 说明 |
|---|---|---|
| 封存 holdout（模板内 120 条） | 117/120（候选） vs 103/120（基座） | 模板内效果好 |
| 分布外（模板外 60 条） | 35/60（0.5833） | **大幅下降** |
| OOD 表达变化类（20 条） | **0/20** | 比零训练基座（6/20）更差 |
| ~~退化曲线（6/9/12/15 工具）~~ | ~~全部 0.45~~ | **读数作废**（2026-08-27，LOG-20260827-01）：四点逐位相同是自变量空转的指纹，不是平坦 |
| R6 措辞增强后封存违规 | 2–7 次（同配置两次运行） | 安全性下降 |

**核心矛盾**：模板内 120/120 → 模板外 0.5833 → 表达类 0/20。模型学到的是「这 12 种说法出现时该退款」，不是「什么时候该退款」。

## 二、根因分析

### 根因 1：数据多样性严重不足（主因，权重 50%）

**证据（项目内）**：

1. **训练集只有 12 句模板**。`formal_tasks.py:_user_request` 定义 6 场景 × 2 变体 = 12 句中文祈使句（"请查询订单…""请核实订单…""请检查订单…"），全部是书面正式口吻。train/dev/holdout 共用这 12 句。来源：`src/veritool_rl/retail_ops/formal_tasks.py:508-540`

2. **R6 措辞增强后扩到 ~184 种说法，但分布仍窄**。DeepSeek 生成的措辞池虽然增加了说法多样性，但仍限于「退款」场景的同义改写，没有覆盖口语、中英夹杂、极简、情绪化等真实分布。来源：`findings.md` "R6 泛化修复"

3. **OOD 0.5833 直接证明模板过拟合**。同一个拿到 120/120 的候选，在模板外掉到 0.5833；表达变化类 0/20 比零训练基座（6/20）更差——训练反而把基座原有的多语言鲁棒性挤掉了。来源：`docs/OOD_EVALUATION.md`

4. ~~**退化曲线平坦说明工具数不是瓶颈**~~——**这一条已作废**（2026-08-27，LOG-20260827-01）。N=6/9/12/15 的读数逐位相同（全部 0.45），当时读成"曲线无下降趋势"；实为 `tool_count` 空转，四个断点看到的是同一批任务和同样的 15 个工具。**本诊断的主因归因不依赖这一条**——"数据多样性不足"由第 1–3 条支撑；但"工具数不是瓶颈"这个佐证现在没有证据，需重跑才有。来源：`findings.md` "C2 退化曲线"

**证据（外部文献）**：

| 项目 | 模型 | 训练量 | 工具/API 数 | 结果 |
|---|---|---|---|---|
| **ToolAlpaca** (Tang et al. 2023) | LLaMA-7B | **3,938 条** | 400+ API / 50 类 | 接近 GPT-3.5 |
| **ToolLLM** (Qin et al. 2023) | LLaMA-2-7B | **126,486 条** | 16,464 API / 49 类 | 接近 ChatGPT |
| **Gorilla** (Patil et al. 2023) | LLaMA-7B | **1,700 条** | 1,645 API | 强 OOD 泛化 |
| **本项目** | Qwen3-4B | **240 条** | **2 工具 / 6 类** | 模板内好，OOD 差 |

ToolAlpaca 的结论：**~4K 条覆盖 400+ API 的数据，比~126K 条覆盖少量 API 的数据泛化更好**。关键不是数量，是**工具/场景覆盖度**。本项目 240 条 / 2 工具 / 12 模板，比所有已发表的 tool-use SFT 工作都小至少一个数量级。

**ToolLLM 的直接对比**（三种数据构建策略）：
- I1（87K 单工具指令）：检索准确率最高，**跨类别泛化最差**
- I3（25K 跨类别多工具组合）：**泛化最强**
- 结论：**多工具组合多样性 > 模板多样性 > 原始数量**

**判定**：240 条 / 12 模板 / 2 工具是**结构性不足**，不是「再多一点就好」。需要至少扩到：
- **工具数**：10+ 类不同工具（不仅是退款族内的变体）
- **场景数**：20+ 类不同任务（不仅是退款的 6 种形态）
- **模板数**：每类 5-10 种不同口吻（书面/口语/极简/情绪化/中英混合）
- **总训练量**：至少 2,000-5,000 条高质量、多样的样本

### 根因 2：SFT 方法论的固有限制（次因，权重 30%）

**证据（项目内）**：

1. **2×3 矩阵证明 prompt 与训练解决不同问题**。prompt 把 refund_eligible 从 5→9/10（解除「不敢执行」），训练把 refund_recovery 从 5→10/10（教会「失败后重试」）。但两者都不能教会「理解用户真实意图」——那是 OOD 表达类 0/20 的根因。来源：`findings.md` "R4 第三轮"

2. **LoRA 容量与模型规模耦合**。4B 上全 linear 最好（60/60），1.7B 上 attention-only 最好（58/60），全 linear 让拒绝类从 30/30 崩到 15/30。不存在「越大越好」。来源：`docs/RESUME_EVIDENCE.md` §1.2b

3. **SFT 本质是行为克隆，不是推理学习**。训练数据是「状态 → 工具调用 → 结果 → 回复」的线性轨迹。模型学到的是这个序列的表面模式，不是「为什么在这个状态下应该调这个工具」的推理。OOD 集上 code_switch 1.00→0.00 直接证明：换个口吻就不会了。来源：`docs/OOD_EVALUATION.md`

**证据（外部文献）**：

- **QLoRA 论文**（Dettmers et al. 2023）：「a small high-quality dataset leads to state-of-the-art results」——但这里的前提是「高质量」意味着**覆盖了目标分布**。240 条 12 模板没有覆盖目标分布。
- **LIMA**（Zhou et al. 2023）：1,000 条精心策划的数据教会 65B 模型特定响应格式——但那是格式学习，不是决策边界学习。退款拒绝需要理解**边界条件**（什么时候该拒绝），比格式学习难得多。
- **ToolLLM 发现**：没有 DFSDT 推理轨迹的模型「学会了调 API 但不能从错误中恢复」——本项目的 refund_recovery 类（需要重试）正是这个失败模式。

**判定**：SFT + QLoRA 在当前数据规模下，能学会**格式和简单映射**（lookup/denied 类全对），但学不会**条件决策和错误恢复**（eligible/recovery 类失败）。这是方法论在小数据下的固有限制，不是调参能解决的。

### 根因 3：代码工程约束（辅因，权重 20%）

**证据（项目内）**：

1. **parser 禁止「文本 + 工具调用」同时出现**。`parser.py:29-31`：如果 `<tool_call>` 标签外还有文本，返回 `mixed_tool_call_content` 错误。这意味着模型不能「先说一句话再调工具」——而这恰恰是真实场景中常见的行为（"让我帮您查一下…"然后调 get_order）。来源：`src/veritool_rl/core/agent/parser.py:29-31`

   **影响**：训练数据中 assistant 的工具调用消息 `content` 必须为空。这限制了训练数据的多样性——无法生成「先解释再执行」的轨迹。

2. **`max_steps=4` 硬编码**。`formal_tasks.py:139`：所有任务的 `max_steps=4`。对于需要 3 次工具调用的 refund_recovery（get_order → refund_order 失败 → refund_order 重试），只剩 1 步余量。如果模型在任何一步说了「最终答复」，episode 立即终止。来源：`src/veritool_rl/retail_ops/domain/formal_tasks.py:139`

   **影响**：多步任务的容错空间极小。模型说一句「我来帮您处理」就被判为 FINAL_RESPONSE（失败），即使它打算下一步执行。

3. **`verify_final_state` 要求状态精确匹配**。`environment.py:70`：`state_matches = self._state == self._task.target_state`——要求环境状态与目标状态**逐字段相等**。任何一个字段不匹配就判失败。来源：`src/veritool_rl/retail_ops/domain/environment.py:68-77`

   **影响**：模型必须精确执行 exactly the expected tool calls，不能有任何偏差。这在简单任务上没问题，但在复杂场景下（如需要选择正确 reason 参数），一个参数错误就全盘失败。

4. **`refund_order` 的 reason 参数必须精确匹配**。任务期望 `reason=damaged`，如果模型传 `reason=wrong_item`（语义相似但不精确），`target_state` 不匹配，判失败。来源：项目测试中多次观察到此类失败

   **影响**：模型不仅要选对工具，还要选对参数值。在 4 个 reason 值中随机猜的准确率是 25%。

**判定**：工程约束不是主因，但它们**放大了数据不足的问题**。parser 约束限制了训练数据的表达力，max_steps 限制了多步任务的容错，精确状态匹配提高了单条任务的难度。如果数据充足，这些约束可以容忍；在数据不足时，它们让每条训练样本的信息量更低。

## 三、三个根因的交互关系

```
数据不足（12 模板 / 2 工具 / 240 条）
    ↓
SFT 只能学到表面模式（模板 → 动作映射）
    ↓
OOD 泛化失败（0.5833 → 表达类 0/20）
    ↓
同时，工程约束（parser / max_steps / 精确匹配）
    ↓
进一步压缩了每条训练样本的信息量
    ↓
模型需要更多数据才能学到相同的决策边界
```

**关键洞察**：三个根因不是独立的，而是**相互放大**的。数据不足是主因，但工程约束让数据不足的问题更严重。如果只扩数据不改工程约束，改善会有限；如果只改工程约束不扩数据，同样有限。**两者需要同时做。**

## 四、改进方向与预期效果

### 方向 A：扩大任务集（解决根因 1）

**做什么**：
- 工具数从 2 扩到 10+（不同 API 类别：订单、退款、物流、客服、库存…）
- 场景数从 6 扩到 20+（不只退款，覆盖查询/修改/取消/升级/…）
- 模板数从 12 扩到 100+（每类 5-10 种口吻：书面/口语/极简/情绪化/中英混合）
- 总训练量从 240 扩到 2,000-5,000 条

**预期效果**：OOD 表达类从 0/20 提升到至少 10/20（参考 ToolAlpaca 在 4K 条数据上的表现）

**风险**：需要重新冻结数据集、重新采集 teacher、重新训练。已有的全部 evidence 失效。

### 方向 B：放宽工程约束（解决根因 3）

**做什么**：
- parser 允许「文本 + 工具调用」（改为 warning 而非 error）
- max_steps 从 4 提到 6-8（给多步任务更多容错空间）
- 状态匹配从精确匹配改为关键字段匹配（只比对 refund_status 等关键字段）

**预期效果**：单条任务的通过率提升，但不解决 OOD 泛化问题

**风险**：放宽 parser 会改变训练数据格式；放宽 max_steps 会改变评测一致性。

### 方向 C：换方法论（解决根因 2）

**做什么**：
- 从 SFT 换成 DPO/RLHF（需要偏好数据）
- 或者从 scratch pretrain（不现实，资源不够）
- 或者用 in-context learning（给模型 few-shot 示例而不是 SFT）

**预期效果**：可能改善泛化，但需要全新的数据 pipeline 和训练流程

**风险**：成本高、周期长、不确定性大。不建议作为首选。

---

## 五、建议的优先级

| 优先级 | 方向 | 理由 |
|---|---|---|
| **P0** | 扩大任务集（方向 A） | 主因，文献支持，预期效果最确定 |
| **P1** | 放宽 max_steps + parser（方向 B 的一部分） | 低成本，立即可做，不改变数据 |
| **P2** | 换方法论（方向 C） | 高成本，不确定性大，留作后续 |

**建议先做 P0 + P1 的组合**：扩大数据集的同时放宽工程约束，看效果是否有质的提升。如果 P0+P1 后 OOD 仍然差，再考虑 P2。
