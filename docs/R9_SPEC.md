# R9 Spec v2：效果提升——数据多样性扩展实验

**版本**：2.0（经三轮独立校验修订）
**日期**：2026-08-21
**前置文档**：`docs/R8_DIAGNOSIS.md`（根因分析）、v1.0 三轮校验记录

## 0. 修订说明（基于三轮独立校验）

v1.0 被三轮校验指出以下核心问题：

| 问题 | 来源 | 修订 |
|---|---|---|
| 声称"单因素"但同时改变 5 个变量 | ML reviewer | 拆为两阶段：Phase A（纯数据量）→ Phase B（数据多样性） |
| 缺少 volume-only 控制臂 | ML reviewer | Phase A 就是 volume-only 控制（2000 条 / 3 工具 / 6 场景） |
| RetailOpsEnv 无法支持 10 工具 | Engineering reviewer | Phase B 限制在 5 工具（零售族内扩 2），不做跨域 |
| API 成本估算偏低 10-20x | Engineering reviewer | 修正为 $5-12 |
| 工具扩展需用户确认 | Release reviewer | 在 Phase B 启动前设置显式审批门 |

---

## 1. 背景与目标

### 1.1 当前问题

R8 诊断确认效果不佳的主因是数据多样性不足（240 条 / 12 模板 / 2 工具）。
OOD 表达类 0/20、总分 0.5833，模板内 120/120 无法泛化。

### 1.2 目标

分两阶段做扩展实验：
- **Phase A**：只增加数据量（240→2000），保持工具/场景/模板不变 → 验证"数据量"的独立贡献
- **Phase B**：增加数据多样性（3→5 工具，6→12 场景，12→60+ 模板） → 验证"多样性"的独立贡献

**核心问题**：OOD 泛化差，究竟是数据不够多，还是数据不够多样？

### 1.3 非目标

- 不换模型（仍是 Qwen3-4B + QLoRA）
- 不换训练方法（仍是 SFT）
- 不做封存 holdout 观测
- 不改发布门禁阈值
- 不改 parser / max_steps / verify_final_state（Phase A+B 均不改）

## 2. Phase A：数据量消融（纯 volume effect）

### 2.1 设计

**唯一变量**：训练样本数。工具、场景、模板、口吻、工程约束全部不变。

| 维度 | baseline | Phase A | 变化 |
|---|---|---|---|
| 训练量 | 240 条 | **2,000 条** | ×8.3 |
| 工具 | 2 个 | 2 个 | 不变 |
| 场景 | 6 类 | 6 类 | 不变 |
| 模板 | 12 句 | 12 句 | 不变 |
| 口吻 | 书面正式 | 书面正式 | 不变 |
| epoch | 3 | 3 | 不变 |
| 梯度步数 | ~75 | ~600 | ×8（由数据量自然增长） |

**实现方式**：对现有 240 条训练数据做 oversampling：
- 每条原始样本通过 **不同的 order_id/reason/margin 组合** 生成变体
- 保持 user_request 模板不变（仍是那 12 句），只替换实体
- 目标 2,000 条，去重后保留唯一模板+实体组合

**为什么 oversampling 而不是生成新模板**：Phase A 的目的就是隔离"数据量"的效果。如果同时引入新模板，就无法区分"更多数据"和"更多样数据"的贡献。

### 2.2 评测

| 评测集 | 条数 | 说明 |
|---|---|---|
| dev（模板内） | 60 | 不变 |
| OOD v2（模板外） | 60 | 不变 |
| **新增：oversampled OOD** | 60 | 用与训练集相同的 12 模板但不同的实体组合，测试实体泛化 |

### 2.3 预期与判读

| 结果 | 判定 |
|---|---|
| OOD ≥ 0.70 | 数据量是重要因素，继续 Phase B |
| OOD 改善但 < 0.70 | 数据量有帮助但不够，Phase B 必须做 |
| OOD 无改善 | 数据量不是瓶颈，需重新诊断 |

## 3. Phase B：数据多样性扩展（需用户确认后启动）

**前置条件**：Phase A 完成 + 用户确认同意扩展工具集。

### 3.1 设计

在 Phase A 的 2,000 条基础上，增加工具和场景多样性。

| 维度 | Phase A | Phase B | 变化 |
|---|---|---|---|
| 训练量 | 2,000 条 | **2,500 条** | +25% |
| 工具 | 2 个 | **5 个** | +3（族内扩展） |
| 场景 | 6 类 | **12 类** | +6 |
| 模板 | 12 句 | **60+ 句** | ×5（5 种口吻 × 12 类） |
| 口吻 | 书面正式 | 书面/口语/极简/情绪化/中英混合 | 5 种 |

**工具扩展**（零售族内，不做跨域）：

| 工具 | 来源 | 说明 |
|---|---|---|
| get_order | 已有 | 不变 |
| refund_order | 已有 | 不变 |
| get_store_hours | 已有 | 不变 |
| get_refund_status | **新增** | 查询退款状态（与 get_order 有语义重叠） |
| cancel_order | **新增** | 取消订单（与 refund_order 有语义重叠） |

**场景扩展**（6→12）：

| 原有 6 类 | 新增 6 类 |
|---|---|
| lookup_status | check_refund_status（需要 get_refund_status） |
| refund_eligible | cancel_eligible（需要 cancel_order） |
| refund_denied_window | cancel_denied_recent（取消最近订单被拒） |
| refund_denied_ownership | cancel_denied_in_use（订单使用中被拒） |
| refund_denied_duplicate | refund_then_cancel（退款后取消关联订单） |
| refund_recovery | cancel_recovery（取消失败后重试） |

**关键设计**：新增工具与原有工具有**语义重叠**（get_refund_status vs get_order 都能查退款信息），模型需要学会在多个可能的工具中选择正确的那个。

### 3.2 评测

| 评测集 | 条数 | 说明 |
|---|---|---|
| dev（原有 6 类） | 60 | 不变，用于检测退化 |
| OOD v2（模板外） | 60 | 不变 |
| **新增：跨工具 OOD** | 40 | 5 工具场景，测试工具选择泛化 |
| **新增：多步组合** | 30 | 需要 3+ 步的跨工具任务 |

**注意**：跨工具 OOD 测试的是**训练集中出现过的工具**在新场景下的表现，不是真正的 OOD（那是 11th tool 的测试，本轮不做）。指标名称改为"cross-tool generalization"以避免误导。

### 3.3 预期与判读

| 结果 | 判定 |
|---|---|
| OOD ≥ 0.80 + 跨工具 ≥ 0.70 | 数据多样性是主因，可考虑继续扩大 |
| OOD 改善但跨工具差 | 多样性有帮助但跨工具组合需要更多数据 |
| 任意评测集下降 | 新工具引入了干扰，需要更精细的数据平衡 |

## 4. 通用设计

### 4.1 数据生成流程

```
1. 定义模板变体（Phase A: 实体替换；Phase B: + 新场景 + 新口吻）
2. 用 teacher（DeepSeek）生成轨迹
   - 每条：user_request → tool_call(s) → observation → final_response
   - 验证：可重放、状态匹配
3. 质量门：teacher 通过率 ≥ 85%
4. sha256 切分 train/dev/holdout（80/10/10）
```

### 4.2 评测指标

| 指标 | baseline | Phase A 目标 | Phase B 目标 |
|---|---|---|---|
| dev task_success | 0.967 | ≥ 0.95 | ≥ 0.95 |
| OOD task_success | 0.583 | **≥ 0.70** | **≥ 0.80** |
| OOD expression_ood | 0.00 | ≥ 0.20 | **≥ 0.50** |
| policy_violation | 2-7 | ≤ 5 | ≤ 3 |

### 4.3 判读规则（在看到结果前写定）

**Phase A**：
| 结果 | 判定 | 后续 |
|---|---|---|
| OOD ≥ 0.70 | 数据量是重要因素 | 进入 Phase B |
| OOD 改善但 < 0.70 | 有帮助但不够 | 必须进入 Phase B |
| OOD 无改善 | 数据量不是瓶颈 | 跳过 Phase B，重新诊断 |

**Phase B**：
| 结果 | 判定 | 后续 |
|---|---|---|
| OOD ≥ 0.80 且 expression_ood ≥ 0.50 | 多样性是主因 | 考虑扩大到 5000+ 条 |
| 改善但 < 目标 | 有帮助但需更多 | 增加口吻种类或工具数 |
| 任意评测集下降 | 新工具引入干扰 | 分析失败模式，调整数据平衡 |

### 4.4 资源估算

| 项目 | Phase A | Phase B | 合计 |
|---|---|---|---|
| API 费用（DeepSeek） | ~$3-5 | ~$2-3 | **$5-8** |
| GPU 训练时间 | ~15 min | ~10 min | ~25 min |
| GPU 评测时间 | ~20 min | ~25 min | ~45 min |
| CPU 数据生成 | ~2h | ~3h | ~5h |

### 4.5 风险与缓解

| 风险 | 缓解 |
|---|---|
| Oversampling 导致过拟合 | Phase A 的 OOD 评测专门检测这个 |
| 新工具引入导致已有能力退化 | 保留原有 60 条 dev 集不变，可检测退化 |
| Teacher API 费用超预期 | 先做 200 条 smoke 确认单条成本 |
| 数据质量不达标 | 质量门 ≥ 85% 通过率，不达标则重采 |

## 5. 执行顺序

```
Phase A:
1. Oversample 240→2000 条（CPU，实体替换，不改模板）
2. Teacher 验证子集（200 条，确认通过率）
3. 训练 Phase A 候选（GPU，~15min）
4. Dev + OOD + oversampled OOD 评测（GPU，~20min）
5. 分析 → 决定是否进入 Phase B

Phase B（需用户确认）:
6. 定义 5 工具 schema + 12 场景模板（CPU）
7. Teacher 采集 2500 条（GPU + API，~$3）
8. 训练 Phase B 候选（GPU，~10min）
9. 全套评测（GPU，~25min）
10. 对比分析 + 报告
```

## 7. 本轮实验的诚实边界

1. **这不是严格的消融实验**。Phase A 改了数据量，Phase B 改了多样性，但每个 Phase 内部仍有多个变量同时变化（如 Phase B 同时改了工具数、场景数、模板数、口吻数）。结果只能说明"这组变化有没有帮助"，不能精确归因到单个维度。
2. **梯度步数随数据量自然增长**。240×3 epoch = 75 steps，2000×3 = 600 steps。Phase A 的效果可能来自更多优化步数而非更多数据。要真正分离需要控制梯度步数（如 240 条 × 25 epoch = 600 steps），但那会让 Phase A 的 baseline 训练时间大幅增加，本轮不做。
3. **本轮不做 10+ 工具**。工程评审确认 RetailOpsEnv 扩到 10 工具需要重构环境状态模型和验证逻辑，成本远超本轮范围。5 工具是本轮上限。
4. **结果不用于发布判定**。本轮结论是探索性的，不消耗封存 holdout，不替换当前候选。
