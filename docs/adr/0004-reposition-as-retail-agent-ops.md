# ADR 0004: 重定位为 RetailAgentOps 工程交付流水线

- 状态: 已接受
- 日期: 2026-07-20
- 替代: ADR 0003 中“禁止根 AGENTS.md”的入口约束

## 背景

旧 VeriTool-RL 路线以研究型后训练、多个 seed 和算法消融为主。用户的当前目标是在三个月内为
Agent 求职交付可运行工程项目，而不是继续产出论文；共享 4× RTX 4090 也不能作为持续独占资源。
现有 MiniRetail、BFCL、QLoRA 和 provenance 资产有用，但无法单独回答真实团队为何采用。

## 决策

项目对外名改为 RetailAgentOps，产品闭环固定为零售工具 Agent 的 `build -> evaluate -> release ->
serve`。默认以单卡、一个开发 seed 完成迭代，用独立重建验证最终简历数字；偏好优化只有在失败证据
满足触发条件后才进入计划。创建根 `AGENTS.md` 作为 Codex 主入口，`CLAUDE.md` 保持兼容。

## 结果

- 前六周以可部署的垂直 Agent 和发布门禁为验收，不以论文或榜单为验收；
- 固定 holdout、关键政策违规、非法工具调用、延迟和证据完整性共同决定发布；
- 旧研究报告与多 seed 路线保留在原目录并用哈希清单追溯，不进入活动分支；
- Python 包名暂留 `veritool_rl`，避免产品初始化混入机械重命名。

## 弃选方案

1. 继续以 GRPO/多 seed 为主线：算力和时间不匹配，也缺少工程使用者。
2. 只包装现有 BFCL 结果：缺少零售业务闭环和服务交付，难以回答应用价值。
3. 立即重命名所有 import：不增加产品证据，却扩大迁移风险。
