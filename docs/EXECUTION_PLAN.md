## 状态约定

- `当前`：允许实施的阶段，同一时间只有一个。
- `待执行`：前置未通过，不得提前启动。
- `条件执行`：满足触发条件并获得用户确认后才允许。
- `已完成`：验收目标全部有证据，后续只能追加更正记录。
- `已阻塞`：停止资源消耗，记录证据并等待用户或外部条件。

## R1 产品契约与 v0.1（已完成）

**总体目标**：用现有 MiniRetail 和 CPU 可测组件打通 `build → evaluate → release → serve` 的最小工程闭环，不进行正式训练。

**执行目标**：

- 与用户冻结 RetailOps v1 的工具、政策、任务类别、数据来源和 holdout 规则；
- 定义 domain bundle、run manifest、release policy 和 evidence bundle 契约；
- 实现 CLI/API 的最小入口，base/oracle/fake candidate 可走相同评测和门禁；
- 输出逐任务结果、失败分类、资源字段和 HTML/Markdown 发布报告；
- 为非法工具调用、政策拒绝、状态错误、超时和 manifest 篡改补测试。

**验收目标**：

- 用户已确认任务契约和冻结规则，Agent 未自行决定数据规模；
- 一个命令可从 bundle 生成完整评测与 GO/NO-GO 证据；
- 相同输入重复运行的任务集合、门禁和报告一致；
- 100% 运行有 manifest、逐任务证据和失败类别；
- 本地只使用 CPU，未下载新模型。

## R2 数据与评测流水线

**总体目标**：建立可以支撑领域适配的执行有效数据和独立冻结评测，不把生成文本直接当训练数据。

**执行目标**：

- 执行 replay、最终状态与政策校验，过滤无效、重复、泄漏和不可复现轨迹；
- 冻结 train/dev/holdout manifest、哈希和 evaluator；
- 建立 Qwen3-1.7B 与计划主模型的 base 评测；
- 报告覆盖、执行通过率、失败 taxonomy、延迟、显存和 API 成本。

**验收目标**：

- 训练轨迹 100% 通过 schema，进入训练的成功轨迹 100% 可执行重放；
- train/dev/holdout ID 和派生内容无交叉，holdout 不进入开发分析输入；
- base 报告可由固定 manifest 和命令重建；
- 数据规模、类别比例和 teacher 选择已经用户确认；
- 任何泄漏、evaluator 不稳定或政策不可验证问题触发阶段阻塞。

## R4 失败驱动优化

**总体目标**：只针对 R3 中数量足够、可观测、可复现的主要失败类别做一到两项高收益改进。

**执行目标**：

- 冻结失败 taxonomy 和优先级，先检查数据覆盖、模板/parser、工具 schema 和 verifier；
- 每轮只改变一个主要变量，使用相同任务、预算和 evaluator 配对比较；
- 只有稳定失败类别能形成足量执行有效偏好对且 SFT 已停滞时，才提出 DPO 方案等待用户确认；
- 不进入 GRPO/在线 RL；
- 对随机 user simulator 任务做 3 次 episode 重放，确定性任务不重复。

**验收目标**：

- 每个改动对应明确失败类别、影响文件、成本和停止条件；
- 最多两轮主要改进，未达到预设收益即停止而非扩展算法；
- 最终候选若要在简历写提升，必须完成一次独立重建并保持正向结果；
- 负结果、回归和被放弃方案完整记录。

**实际执行（三轮，2026-08-11 至 08-14）**：

- 第一轮（数据比例重平衡）判负并按预设停止条件停止（LOG-20260811-09）；
- 第二轮三候选并列消融（容量 / 数据闭环 / 指令框定），只有容量一项达标（LOG-20260814-01、-02）；
- 第三轮补齐同 prompt 配对与跨规模验证，**证伪了第二轮的一般化结论**（LOG-20260814-03、-05）；
- 第二次封存 holdout 观测与判定：候选 120/120、`success_delta` +0.1417，
  但 `p95_latency_ratio` 1.8774 > 1.25 → **NO-GO / baseline**（LOG-20260814-04）；
- 「最多两轮」这一条被实际执行超出：第三轮是为修补第二轮的方法缺口（对照了旧 prompt 的
  base）而开的，属方法修正而非算法扩展，且未消耗额外 holdout 观测。

## R4.5 架构补强（已完成）

**总体目标**：把 2026-08-15 外部视角评审的 13 条问题逐条收口。评审总判断是"这是一个
优秀的模型交付治理项目，但目前不是一个 Agent 架构项目"——全部工程复杂度集中在证据链
与发布纪律上，而 Agent 本体是 3 工具、单轮、最多 5 步、正则解析的最小 ReAct 循环。

**与 R4 的性质差异**：R4 是"改模型让候选达标"，本轨道是"补齐系统本身的架构缺口"。
**没有一项以候选通过发布门禁为成功标准**，也不得因此下调任何阈值。

**执行目标**：

- 批次 1（纯 CPU）：serve 从演示夹具补成服务、CI 与容器化、交付文档单一事实源、
  `verifier_reward` 降级为诊断量；
- 批次 3（纯 CPU）：发布门禁语义**版本化**升级——拆分延迟门禁、引入配对统计检验，
  v1.0 集合逐字节冻结以保证已有 release 报告仍可加载；
- 批次 2：业务政策外置为可执行规则、退款幂等键、独立 guardrail 层与注入评测；
- 批次 4：分布外 holdout、serving 形态对照（merge / vLLM）、Agent 能力面扩展。

**验收目标**：

- 评审 13 条每条都有明确归宿：已完成 / 已完成但受限 / 被用户否决 / 未做及原因；
- 阈值一个字不改（锁在 `test_thresholds_come_from_the_untouched_release_yaml`、`invalid_call_count_max: Literal[0]` 与 `release.yaml` 进 `bundle_sha256` 三层）；
- 旧口径下的两次 NO-GO 结论保留不改写；新口径产生不同结论时两者并列陈述；
- 已有 release 报告与 sealed 证据在改动后仍能被加载；
- 第三次封存 holdout 观测默认不做；**若要消耗，须用户单独决策，且在所有代码改动
  冻结并提交之后一次性进行**。
  实际执行：用户于 2026-08-15 裁定消耗，观测在 `b529bc9` 冻结点之后一次跑完三次运行
  （base / candidate / 合并版部署形态探针），判定 **NO-GO**（LOG-20260815-03）。

**进度（2026-08-16）**：评审 13 条已全部收口；批次 1–4 均已执行。
**907 tests passed**（起始 698；R4.5 收口时的实测值，此前本行写的 901 是批次 3 完成时的中间值）。关键结果：

- 封存 holdout 前四次观测：前三次 **NO-GO**，第四次（**合并部署形态**）拿到项目历史上
  第一个 **自动门禁 GO**（LOG-20260815-04）。GO 归因于部署形态而非模型——未合并形态
  对同一 base 重算仍 FAIL 1.9219。
- **sealed 证据契约版本化到 v1.1**，让合并形态可进配对，且七份旧证据的 `report_id`
  复算逐位不变。
- **分布外任务集证明 120/120 不是泛化**（LOG-20260816-01）：同一候选掉到 0.5833，
  表达变化一类 **0/20**、比零训练基座还差；而场景/对抗两类从 0.00/0.35 升到 0.75/1.00。
  结论是这次 SFT **用表面形式鲁棒性换来了任务结构与安全性**。
- **serving 四档已跑满**（LOG-20260816-02）：合并 + vLLM 相对当前服务栈是 3.32×，

- **引擎替换不保行为**（LOG-20260816-03）：vLLM 走完整 evaluate 路径（dev + OOD，
