## 2. dev 60 与 holdout 120 的关系

**dev 60 不是 holdout 120 的子集；选择是确定性的，不是人为挑"容易"的。**

数据来源（`formal_tasks.py:build_formal_task_set`）：
- 6 场景 × 35 family（7 state_variant × 5 context_variant）= 210 family；
- 每 family 2 变体 = 420 task；
- 按 `family_fingerprint` 排序后，前 20 family → train（240 task），中间 5 family → dev（60 task），最后 20 family → holdout（120 task）。

隔离验证：
- `formal_tasks.FormalTaskSet.assert_exact_quotas` 断言 `task_fingerprint`、`content_fingerprint`、`family_fingerprint`、`source_fingerprint`、`derivation_fingerprint` 五维指纹跨 split 零重叠；
- `formal_manifests.assert_formal_split_isolation` 在 manifest 层再次断言同样五维；
- `dataset.json` 的 `public_files_sha256` 绑定三份 split 文件的 SHA-256。

v4（12 场景）同理：12 × 35 × 2 = 840 task，train/dev/holdout = 480/120/240。

**潜在问题**：dev 和 holdout 虽然指纹不重叠，但共享相同的取值域（margin ∈ {1,2,3,5,7,10,14}，order status ∈ 7 种，distractor_count ∈ {0,1,2,3,4}）。这意味着"容易"和"难"的任务在两个 split 里按相同分布出现——dev 不是 holdout 的子集，但两者覆盖同一片状态空间。这不是 bug（设计如此：同源分布才是 fair comparison），但引用 dev 读数推断 holdout 行为时必须意识到这一点。

## 3. 多个评测集的交叉

**task_id 和 split 字段阻止了直接 ID 重叠；内容重叠是设计意图而非 bug，但缺少自动化断言。**

评测集清单：

| 集合 | 任务生成器 | task_id 格式 | split | 任务数 |
|---|---|---|---|---|
| v1 正式 | `formal_tasks.py` | `sha256(task_identity)` | train/dev/holdout | 240/60/120 |
| v4 正式 | `formal_tasks.py` | `sha256(task_identity)` | train/dev/holdout | 480/120/240 |
| OOD v1 | `ood_tasks.py` | `sha256(expression/scenario/adversarial:seed:index)` | test | 60 |
| OOD v2 | `ood_v2_tasks.py` | `sha256(oodv2:seed:scenario:index)` | test | 60 |
| OOD v4 | `ood_v4_tasks.py` | `sha256(oodv4:seed:scenario:index)` | test | 120 |
| 政策边界 | `policy_boundary_tasks.py` | 自定义 | test | 120 |
| v3 退化曲线 | `v3_tasks.py` | `{scenario}-{split}-{order_id}-{margin}` | train/dev | 按断点变 |

task_id 格式各不相同，且 hash 输入包含各自的数据集版本字符串，理论上不可能碰撞。split 字段也不同（正式用 train/dev/holdout，OOD 用 test，v3 用 train/dev）。

**未覆盖项**：
- 没有测试断言 OOD v1 与 OOD v2 的 task_id 不重叠（虽然格式不同几乎不可能碰撞）；
- 没有测试断言 OOD v2 与 OOD v4 的 task_id 不重叠（同样几乎不可能但未验证）；
- 政策边界探针与正式数据集共享底层状态空间（同源措辞），这在模块说明中已声明，但没有测试验证两者的 task_id 不重叠。

## 4. 评测脚本的确定性

**确定性分两层：任务生成和指标计算是确定性的；模型推理不是。**

确定性部分：
- `formal_tasks.build_formal_task_set`：纯 SHA-256 哈希，完全确定性。测试 `test_retail_ops_formal_tasks.py` 断言两次调用产出相同结果；
- `v3_tasks.build_toolcount_task_set`：纯哈希，确定性。测试 `test_retail_ops_v3_tasks.py::test_deterministic` 断言；
- `compute_metrics`：bootstrap 使用固定 seed（`RELEASE_BOOTSTRAP_SEED=0`），完全确定性；
- `replay_trajectory`：确定性环境重放，结果逐字段校验。

非确定性部分：
- 模型推理（`QwenPolicy`）即使 seed 固定，GPU 浮点运算也可能有微小差异；
- 因此同一模型在同一评测集上两次运行可能给出不同 `trajectory.success`；
- 但 replay 验证会检查轨迹是否可重放——如果推理结果变了，replay 会失败。

**实际影响**：dev 60 上的「58–60/60，三次同配置运行」波动正是这个机制的体现（LOG-20260817-07）。这不是 bug，是已知的 ±2 运行间波动。

## 5. 评测指标的计算

**"最终状态任务成功率"的计算逻辑正确，但有两个边界情况值得注意。**

主指标 `task_success`（`metrics.py:compute_metrics`）：
```python
successes = [float(trajectory.success) for trajectory in trajectories]
task_success = float(successes.mean())
```

`trajectory.success` 由 `runner.py:run_episode` 设置：
```python
success = termination is TerminationReason.SUCCESS
```

`TerminationReason.SUCCESS` 只在 `reward.final_state == 1.0` 时设置（`runner.py:168-169`）。

`reward.final_state` 由 `verifier.py:compute_reward_breakdown` → `env.verify_final_state()` 返回，是 0.0 或 1.0 的二值函数。

**边界情况 1：`task_success` ≠ `final_state_success`**

`compute_metrics` 同时计算：
```python
final_successes = [
    float(bool(trajectory.steps) and trajectory.steps[-1].reward.final_state == 1.0)
    for trajectory in trajectories
]
final_state_success = _mean(final_successes)
```

两者可以不同：如果模型在最后一步达到了正确状态但 `termination` 是 `STEP_LIMIT`（因为没有发出最终答复），则 `task_success=False` 但 `final_state_success=True`。这种情况在 INFORM/DENY 类任务上尤其可能发生——模型完成了查证但没说话。

**边界情况 2：部分成功不算成功**

`verify_final_state` 要求 `state_matches = self._state == self._task.target_state`——必须是精确字典匹配。模型完成了 3/4 步但漏了最后一步，得 0 分。没有部分成功的概念。`verifier_reward` 的 `milestone` 分量度量了 gold 调用完成比例，但已降级为诊断量，不得用于候选选择。

## 6. `skip_reads_gate` 配置

**已移除，有回归测试，但存在一个间接风险。**

已修复：
- `skip_reads_gate` 从任务 metadata 中移除；
- `test_retail_ops_v3_tasks.py::TestPolicyGateIsNotTaskData::test_metadata_cannot_disable_the_cancel_reads_gate` 断言设置 `skip_reads_gate=True` 不影响政策守卫行为。

间接风险：
- `v3_tasks.py` 中 `REFUND_DENIED_WINDOW` 的 margin 变换逻辑 `denied_margin = min(margin, 2) if margin >= 10 else margin` 会在 margin ≥ 10 时将 margin 截断为 2。这不是 `skip_reads_gate`，但它改变了任务的实际难度分布——margin=10 和 margin=14 的任务在 v3 中都被当成 margin=2 处理。v1/v2 没有这个截断。这意味着 v3 的 `REFUND_DENIED_WINDOW` 场景比 v1/v2 更容易（所有超期任务的窗口都被拉到同一档），退化曲线在该场景上的读数可能高估模型能力。
