# 怎么读这个项目的数字（写给持怀疑态度的人）

这个项目里有几个数字高得可疑：**120/120**、**政策违规 0**、**非法调用 0**、
**schema 合规率 1.0000**、**可重放率 100%**、**teacher 通过率 99.2%**。

在别人的简历里看到这几个数，正确的第一反应是不信。所以这份文件不辩解，
只做三件事：**说清每个数是怎么可能达到的**、**指出它旁边那个不好看的数**、
**写明它不能支持什么结论**。

有一条贯穿全文：**如果这些数字是编的，就不会有 0.00、不会有三次 NO-GO、
不会有 58/60。** 一个愿意把打自己脸的读数写进 README 并用测试强制它与好消息成对
出现的项目，没有动机在别处造假——这不是保证，但它是可以被检验的一致性。

---

## 1. 逐个可疑数字

### 1.1 「封存 holdout 120/120」

| | |
|---|---|
| **为什么可能** | 任务面窄到极致：**2 个业务工具**、6 类任务、**12 句请求模板**，且 train/dev/holdout **共用这 12 句**。跨 split 变化的只有随机订单号、reason 枚举词、期限余量、干扰项数量。贪心解码、无采样。在这样一个集合上满分是**模板内插值**，不是能力上限 |
| **旁边那个不好看的数** | 同一份权重在分布外集合上 **0.5833**，其中「换个说法」一类 **0/20**，**比零训练基座还差** |
| **不能支持什么** | 不能说泛化、不能说可靠、不能说可以上线。`task_success_ci95` 是 **[1.0, 1.0]**——满分的退化区间，那不是显著性证据 |
| **怎么自己查** | `grep -n "_user_request" -A 30 src/veritool_rl/retail_ops/domain/formal_tasks.py` 就能看到那 12 句 |

**这条边界不是被人问出来的，是项目自己测出来的**，而且有测试
（`test_the_go_is_never_quoted_without_the_ood_reading`）强制任何提到那个 GO 的文档
必须同时写出 `0.5833` 与 `0/20`。

### 1.2 「政策违规 0 / 非法调用 0 / schema 合规率 1.0000」三项同时满分

这三项是**格式与安全**类指标，不是能力指标。在一批格式统一、全部经过 replay 校验的
轨迹上做 SFT，把它们压到 0 是**容易**的那一半——R3 的候选就做到了
（41→0、16→0、0.7819→1.0000），而它的**任务成功率同时是下降的**（0.7833→0.7500）。

**因此这三个 0 恰恰证明了一件与直觉相反的事**：格式合规与任务完成是可以彼此独立变动的
两类能力。把它们并列成一串满分来暗示「模型很强」是误导，本项目在
`RESUME_EVIDENCE.md` §2 明确禁止这种写法。

### 1.3 「可重放率 100%」

**这是构造决定的，不是模型质量。** 环境是确定性的，轨迹里记着每一次工具调用与参数；
重放就是把同样的调用再执行一遍，对得上是应该的，对不上说明**评测实现坏了**。

它证明的是「这份证据没被改过、这次运行可以复现」，**不证明模型好**。
真正会因此变红的场景是：有人手改了 `trajectories.jsonl`，或环境有隐藏随机性。

### 1.4 「teacher 通过率 99.2%」

这个数**只属于第二批采集**。完整的两批是：

| 批次 | 请求数 | 成本 | 通过率 |
|---|---|---|---|
| `teacher-smoke-001` | 519 | $0.055 | **211/240 = 87.9%** |
| `teacher-full-001` | 526 | $0.0559 | **238/240 = 99.2%** |
| **合计** | **1045** | **≈$0.111** | — |

而且第一批里 `refund_denied_window` 这一类只有 **12/40 = 30%**——那是一个真实的环境
缺陷（判定依据 `current_day` 从未暴露给模型，任何推理式 Agent 都无解）。
修复后才有 99.2%。**只引用 99.2% 而不提 87.9% 和那个 30%，就是在挑数字**；
本仓库有测试（`test_the_two_teacher_batches_are_never_conflated`）挡住这种写法。

### 1.5 「1000+ 测试」

测试数多不等于覆盖好。这个项目的测试构成偏向**契约与治理**：文档与代码的绑定、
配置键集合的精确匹配、冻结哈希的复算、「种一个违规必须被抓到」的负例。
很多是参数化用例，一个函数展开成多条。

**旁边那个不好看的事实**：外部审阅统计过，747 个测试函数里有 **9 个没有 `assert`**
（都是合法的 must-not-raise 用例）。这个数字我没有藏——它就该被查。

想验证测试不是摆设，最快的办法是**改坏一个东西看它红不红**。本仓库自己做过多次这种
突变验证并记在提交信息里，例如改一个被故障矩阵引用的测试名、把 OOD 总分从 0.5833 改掉。

### 1.6 「对抗类 1.00」

同一次分布外评测里，`adversarial` 是 **1.00** 而 `expression_ood` 是 **0.00**。

如果这组数是编的，不会编成这个样子。**这种极端的不平衡本身就是它没被修饰过的证据**，
而且它指向一个具体机制：训练让模型在「面对脏输入不乱来」上变强，
同时让它在「换种说法还认得出该干什么」上变弱。

### 1.7 「dev 60/60」——这个数已经被我自己改小了

独立重建复验（SPEC §6 第 6 条）跑了两次重训，三次同配置运行的读数是
**60 / 58 / 60**。而且**同一个 seed** 重跑也拿不到逐位相同的权重
（训练代码零改动、数据哈希一致）。

所以正确写法是「**58–60/60，三次同配置运行**」。写单点 60/60 不算撒谎，
但等于把一次运气好的运行当成常数。

## 2. 反过来：哪些数字低得可疑

对称地列一下，免得看起来只在解释好消息。

| 低分 | 是不是实现坏了 | 依据 |
|---|---|---|
| `expression_ood` **0.00** | 不是 | 同一次运行里 `adversarial` 1.00、`scenario_ood` 0.75；失败全部是 `premature_final_response`（模型话说得好好的，就是不调工具） |
| 零训练基座在 OOD v1 上 **0.2167** | 不是 | 该集合混了「工具面做不到的请求」，零训练模型在这类上 0.00 是合理的 |
| 第一轮改进 `refund_eligible` **0/10 → 0/10**（精确零变化） | 不是 | 这是单变量实验的结果，据此判负并停止；`train_loss` 反而更低了（0.3722→0.2198），说明代理量与真实任务解耦 |

## 3. 一个数字要能被相信，需要什么

本项目对每个对外数字的最低要求：

1. **能追到产物**：运行报告的 ID 是它自己全部字段的自哈希，改一字节即加载失败
   （已做篡改测试）；私有产物逐一 SHA-256 绑定（已完整行使过一次，含改一个字节被拒）。
2. **配对有前置条件**：模型 revision、生成参数、数据集版本、code commit、依赖锁、
   system prompt 哈希逐字段相同才允许比较。
3. **口径写在数字旁边**：不可写的表述有清单（`RESUME_EVIDENCE.md` §2），
   且关键几条由测试强制。
4. **坏消息与好消息同权**：四次封存观测里三次 NO-GO，全部保留；
   被自己实验推翻的判断有专门一节（七条）。

**你能自己复核的和不能复核的，边界很清楚**：CPU 全链路 clone 下来就能跑并断言内容
哈希（`scripts/ci/verify_qualification_chain.py`，也能在断网的容器里跑）；
GPU 侧的证据文件与权重**不随仓库分发**，因此那部分你只能看口径、看一致性、
看这个项目愿不愿意说自己的坏话。
