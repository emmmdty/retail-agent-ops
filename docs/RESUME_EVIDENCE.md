# 简历证据（R4.5 收口；holdout 观测次数以 `HOLDOUT_LEDGER.md` 为准）

本文件是简历与面试表述的**唯一取数口径**。规则来自 `docs/CAREER_CONTEXT.md`：
只写实际运行得到的数字；不写 SOTA；不把内部固定子集说成官方榜单；
不把单次成功演示说成生产稳定性；**项目可以输出 NO-GO，能拒绝不合格候选本身是工程价值**。

**本版最重要的变化**：项目的核心结论不再是"某个候选达标"，而是一个 2×2 实验矩阵，
它把**提示词工程**与**后训练**的贡献分离到了类别级。这是绝大多数同类项目给不出的证据形态。

### 1.2 核心结果一：prompt × 容量（**Qwen3-4B，dev 60 条**）

### 1.2b 核心结果二：跨规模验证推翻了"越多投影越好"（**dev 60 条，同一份新 prompt 数据**）

| 模型 | 零训练 base | attention-only | 全 linear layer |
|---|---|---|---|
| **Qwen3-4B** | 54/60（elig 9/10） | 55/60（elig 5/10） | **60/60**（elig 10/10） |
| **Qwen3-1.7B** | 44/60（elig **0/10**） | **58/60**（elig 10/10） | 45/60（elig 10/10） |

**1.7B 上方向完全相反**：attention-only 是强正作用（+14 条），全 linear 几乎无增益。
1.7B 全 linear 的 15 条失败**全部**是"该拒绝却没拒绝"（`refund_denied_ownership`
10/10 全灭），`policy_violation` 0→5，`average_tool_calls` 1.267→2.083——**学过头**，
被训练数据 2:1 的执行偏向带跑，丧失拒绝能力。

**结论：LoRA 容量必须与模型规模匹配，不存在"越大越好"。** 容量不足学不会条件决策，
容量过剩牺牲与主偏向相反的能力。出处：LOG-20260814-05。

### 1.3 类别级因果分解（**这是最有解释力的一张表**）

| 贡献来源 | refund_eligible | refund_recovery | policy_violation | invalid_call |
|---|---|---|---|---|
| 基座（原 prompt，零训练） | 5/10 | 5/10 | 8 | 21 |
| **+ 提示词**（零训练） | **9/10** (+4) | 5/10（**0 变化**） | 5 | **0** |
| **+ 后训练**（全 linear） | 10/10 (+1) | **10/10** (+5) | **0** | 0 |

**一句话**：提示词能解除「判定可退却不敢执行」，但教不会「失败后重试」；
后者只能来自轨迹数据。两者修的是不同的失败，几乎不重叠。

| 判断 | 推翻方式 | 出处 |

| 改 `SYSTEM_PROMPT` 后重新导出即可换掉训练集的 system 消息 | 实测 238/240 条逐字节不变（teacher 证据持久化了 metadata），且不报错——会静默产出变量没生效的数据集 | LOG-20260814-01 |

| **"容量决定训练效果的符号"是一般规律** | **跨规模验证证伪**：1.7B 上 attention-only 是强正作用（44→58）、全 linear 几乎无增益，方向与 4B 相反 | LOG-20260814-05 |

### 1.6 延迟代价的归因（**这条最容易被讲错，务必按此口径**）

候选变慢**不是**因为"多做了工具调用"：

| 量 | base | 候选 | 比值 |
|---|---|---|---|
| average_tool_calls | 1.308 | 1.500 | 1.146 |
| average_turns | 2.042 | 2.167 | 1.061 |
| average_output_tokens | 92.2 | 131.7 | 1.429 |
| average_latency_ms | 1958 | 4457 | **2.276** |
| **单次调用耗时** | **1497 ms** | **2971 ms** | **1.985** |

调用次数只增加 14.6%，而单次调用耗时翻倍。差额来自**全 linear layer LoRA 的推理开销**
（7 个投影层每次前向多做一次低秩矩阵乘）。旁证：第一次观测用 attention-only adapter
（4 投影），p95 比值仅 **1.087**。

**因此 R4 的最终结论是一个真实的效果/延迟权衡**：LoRA 从 attention 扩到全部 linear layer
换来 task_success +14.2pp（120/120 满分、三项安全指标清零），代价是 p95 延迟接近翻倍，
发布门禁据此拒绝上线。

**三次观测均已消耗，封存 holdout 不再有"未观测"状态。**

**第三次观测（2026-08-15，R4.5 代码冻结后）**：任务指标与第二次**逐位相同**，
两套门禁口径都仍是 `NO-GO`。同时把候选的 LoRA 合并回基座后重测——同样 120/120、
调用次数一模一样，单次调用 2946.5 → **1717.7 ms**、p95 比值 2.0250 → **1.2141**。
**但那不是发布判定**：封存判定的契约要求 candidate = 同一基座 + adapter，合并版
结构上无法作为候选。余量只剩 1–3%，而 base 侧 p95 在观测间有 9% 波动。
详见 [`SERVING_FORM_COMPARISON.md`](./SERVING_FORM_COMPARISON.md) 与 LOG-20260815-03。

## 3. 简历 bullet：两个方案（**需你选定**）

两版都只用 §1 的数字。**我推荐方案 B**——§1.2/§1.3 那两张表是这个项目现在最难被复制的部分，
而它们天然属于后训练/算法叙事。

### 方案 A —— 面向 Agent 平台 / Agent Evaluation / 系统开发岗

> **RetailAgentOps｜零售工具 Agent 的单卡适配与发布流水线**（个人项目，Python/PyTorch/FastAPI）
> - 设计并实现 `build / evaluate / release / serve` 四接口流水线，覆盖轨迹数据质检、
>   冻结任务评测、版本化发布门禁与单卡服务；**698** 项测试、Ruff/mypy/依赖锁全绿。
> - 建立**不可伪造的证据链**：运行报告以全字段自哈希为 ID、逐产物 SHA-256 绑定、
>   配对比较前强制校验模型/生成参数/数据/commit 同条件，任一字段被改动即加载失败。
> - 实现封存 holdout 的两段式授权与五维指纹隔离，公开产物为 allowlist 字段集并有
>   泄漏扫描测试；120 条 holdout 在整个开发期**只被观测两次**，各用于一次发布判定。
> - 用真实候选跑通**两次**发布判定，两次都输出 **NO-GO** 并驱动服务回滚到冻结基座
>   （`adapter_loaded=false` 可在 `/health` 核对）：第一次是任务成功率未达 +5pp 门槛；
>   第二次候选在 120 条封存任务上达 **120/120**、成功率 **+14.2pp**、政策违规与非法调用
>   全部清零，但 **p95 延迟比值 1.88 > 1.25** 被门禁拒绝——系统能拒绝一个任务指标完美
>   但延迟超标的候选，这正是发布门禁存在的意义。
> - 把评测系统用于**因果归因**而非仅打分：以 2×2 配对实验分离提示词与后训练的贡献，
>   在类别级证明两者修的是不同失败（提示词 +4、训练 +5，几乎不重叠）。

**主语是系统与证据。** 适合"我们需要有人把 Agent 的评测与上线流程做扎实"的岗位。

### 方案 B —— 面向 Agent 后训练 / 算法工程岗（**推荐**）

> **RetailAgentOps｜零售工具 Agent 的领域适配与失败归因**（个人项目，Python/PyTorch/PEFT）
> - 构建执行式训练数据流水线：商业 API teacher 采集 + replay/最终状态/政策 verifier
>   三重校验，240 条训练轨迹通过率 **99.2%**，成本 **$0.055**；train/dev/holdout
>   五维指纹隔离防派生泄漏。
> - 单卡完成 Qwen3-4B QLoRA-SFT（4-bit NF4，r=16，3 epoch，**223 s**，峰值 **5.64 GB**，
>   adapter **66 MB**），评测推理峰值显存 **3.0 GB**。
> - **以 2×2 配对实验分离提示词工程与后训练的贡献**（prompt × LoRA 覆盖范围，
>   六次运行、每格 60 条冻结任务）：一句显式授权指令使零训练基座的目标类别
>   **5/10 → 9/10**，而"失败后重试"类**零变化**；后训练则把重试类 **5/10 → 10/10**、
>   政策违规 **5 → 0**。两者修的是不同失败，几乎不重叠。
> - **量化出 LoRA 容量与模型规模的匹配关系**：4B 上仅挂 attention 投影时 SFT 对目标类别
>   是净负作用，加上 MLP 三投影后同一份数据、同一组超参从负作用变为 **10/10**；但在
>   1.7B 上**方向相反**——attention-only 反而是强正作用（44/60→**58/60**），全 linear
>   因容量过剩被训练数据 2:1 的执行偏向带跑，拒绝类由 30/30 崩到 **15/30**、
>   `average_tool_calls` 1.27→2.08。**结论是容量必须与规模匹配，不存在"越大越好"**，
>   且数据配比与容量耦合、不能当作两个独立旋钮。
> - 在 120 条封存 holdout 上得到 **120/120**（成功率 **+14.2pp**，政策违规 11→0、
>   非法调用 5→0），但**量化出容量的推理代价**：单次工具调用耗时 1497→2971 ms、
>   p95 比值 **1.88**，超过发布门禁的 1.25 上限，判定 **NO-GO**。已定位代价来自
>   全 linear LoRA 的前向开销而非工具调用增多（次数仅 +14.6%）。
> - 每轮改动前写定收益门槛并按门槛判负，全程被自己的实验推翻**四个**判断（含"根因是
>   数据分布失衡""这个 delta 是训练挣来的""候选慢是因为多做了调用"），据此确立
>   "最终状态与政策 verifier 是唯一主判据，loss/奖励不可代替"——`verifier_reward`
>   已四次与主判据背离。

**主语是模型与归因。** 适合"我们需要有人把领域模型调出来并解释清楚为什么"的岗位。

### 共用的一句话总结（自我介绍开场可用）

> 我做了一条零售工具 Agent 的单卡适配与发布流水线。最有意思的结论不是模型变好了多少，
> 而是我用一组配对实验把"提示词工程"和"后训练"的功劳分开了——一句提示词就解决了
> 大半的"不敢执行"问题，而"失败后重试"只能靠训练；并且发现 LoRA 只挂 attention 时，
> 微调对这个能力其实是**负作用**——但换到 1.7B 上这个结论就反过来了，所以真正的规律是
> 容量得跟模型规模匹配。最终候选在封存测试集上做到了 120/120，但因为推理延迟
> 接近翻倍没过发布门禁，系统判了 NO-GO、回滚到基座——**我认为能拿出有证据的拒绝，
> 比拿出一个没人敢信的提升更有价值**。

## 4. 面试主动交代的四件事

不等对方问，主动说，可信度更高（细节见 `DEMO.md` §4）：

1. **候选没有上线，两次发布判定都是 NO-GO** —— 第二次的候选在封存集上是 120/120、
   成功率 +14.2pp，但 p95 延迟比值 1.88 超过 1.25 的门禁上限。我没有改门禁阈值
   （有测试锁定它与上一版逐字段相同）。**能拿出有证据的拒绝是这套系统的价值所在。**
2. **演示挑的三条成功轨迹不代表能力** —— 同批次另一条 `refund_eligible` 仍然失败，
   基座在 holdout 上是 94/120。
3. **有一个环境缺陷是真实 API 采集才暴露的** —— `refund_denied_window` 场景的判定依据
   `current_day` 从未暴露给模型，任何推理式 Agent 都无解；CPU 测试全走 Oracle 所以没发现。
   真实采集通过率 30% 才暴露，修复后 95%。
4. **我的判断被自己的实验推翻了三次**（§1.4）—— 最值得讲的是第三次：我一度可以用
