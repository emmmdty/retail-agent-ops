## 3. 简历 bullet：两个方案（**需你选定**）

两版都只用 §1 的数字，差别在**把什么放在主语位置**。取决于主投岗位方向。

### 方案 A —— 面向 Agent 平台 / Agent Evaluation / 系统开发岗（推荐）

> **RetailAgentOps｜零售工具 Agent 的单卡适配与发布流水线**（个人项目，Python/PyTorch/FastAPI）
> - 设计并实现 `build / evaluate / release / serve` 四接口流水线，覆盖轨迹数据质检、
>   冻结任务评测、版本化发布门禁与单卡服务；624 项测试、Ruff/mypy/依赖锁全绿。
> - 建立**不可伪造的证据链**：运行报告以全字段自哈希为 ID、逐产物 SHA-256 绑定、
>   配对比较前强制校验模型/生成参数/数据/commit 同条件，任一字段被改动即加载失败。
> - 实现封存 holdout 的两段式授权与五维指纹隔离，公开产物为 allowlist 字段集并有
>   泄漏扫描测试；120 条 holdout 在整个开发期保持零观测，仅在发布判定时使用一次。
> - 用真实候选跑通发布决策：候选将政策违规 **16→0**、非法调用 **41→0**、
>   schema 有效率 **0.78→1.00**，但任务成功率 0.783→0.750 未达 +5pp 门槛，
>   系统据此判 **NO-GO** 并驱动服务回滚到冻结基座（`adapter_loaded=false` 可在
>   `/health` 与每条响应核对），完成允许/拒绝/异常恢复三条流程演示。

**主语是系统与证据。** 适合"我们需要有人把 Agent 的评测与上线流程做扎实"的岗位。

### 方案 B —— 面向 Agent 后训练 / 算法工程岗

> **RetailAgentOps｜零售工具 Agent 的领域适配与失败归因**（个人项目，Python/PyTorch/PEFT）
> - 构建执行式训练数据流水线：商业 API teacher 采集 + replay/最终状态/政策 verifier
>   三重校验，240 条训练轨迹通过率 99.2%；train/dev/holdout 五维指纹隔离防派生泄漏。
> - 单卡完成 Qwen3-4B QLoRA-SFT（4-bit NF4，r=16，3 epoch，**134 s**，峰值 **5.16 GiB**，
>   adapter 23.6 MB），训练前经 smoke → overfit（loss 1.27→0.017）→ 全量三级验证。
> - 在 60 条 dev 与 120 条封存 holdout 上做配对评测，两处一致：格式/安全类失败清零
>   （非法调用 41→0、政策违规 16→0），但需 ≥2 次工具调用的场景回退，
>   `refund_eligible` 20/20 全数失败，失败类型 100% 为过早终止。
> - 提出"训练数据动作分布失衡"假设（关键决策点上 3:1 偏向直接作答）并**设计单变量实验
>   验证**：重采样把该比例拉到 1:1 后目标类别通过数**零变化**，假设被证伪；
>   同轮 `train_loss` 0.37→0.22、`verifier_reward` 0.58→0.75 却与任务成功率反向，
>   据此确立"最终状态与政策 verifier 是唯一主判据，loss/奖励不可代替"，
>   并按改动前写定的收益门槛判负停止，未放宽门槛也未转而扩展算法。

**主语是模型与归因。** 适合"我们需要有人把领域模型调出来并解释清楚为什么"的岗位。

### 共用的一句话总结（自我介绍开场可用）

> 我做了一条零售工具 Agent 的单卡适配与发布流水线，最终交付的结论是一个 **NO-GO**——
> 候选把格式和政策违规清零了，但多步任务完成率不升反降，没过发布门禁，服务自动回滚到基座。
> 我认为能拿出有证据的拒绝，比拿出一个没人敢信的提升更有价值。

## 4. 面试主动交代的三件事

不等对方问，主动说，可信度更高（细节见 `DEMO.md` §4）：

1. **演示挑的三条成功轨迹不代表能力** —— 同批次另一条 `refund_eligible` 仍然失败，
   基座在 holdout 上是 94/120。
2. **有一个环境缺陷是真实 API 采集才暴露的** —— `refund_denied_window` 场景的判定依据
   `current_day` 从未暴露给模型，任何推理式 Agent 都无解；506 个 CPU 测试没发现，
   因为测试全走 Oracle。真实采集通过率 30% 才暴露，修复后 95%。
3. **我曾把推测当结论后被数据推翻** —— 误判基座评测慢是被他人抢 GPU，
   provenance 的 `wall_time_seconds`（287 s vs 544 s）证明候选才更慢，
   基座那 20 分钟主要是冷启动哈希校验。
4. **我对失败根因的第一个判断是错的，而且是我自己的实验推翻的** ——
   我判断根因是训练数据的动作分布失衡，设计了单变量实验（只改训练数据、超参逐字段不变）
   把关键决策点比例从 3:1 拉到 1:1，结果目标类别通过数变化**精确为 0**。
   门槛是改动前写定的，达不到就停，没有事后调门槛、没有改判据、没有转去堆算法。
   这一轮的产出是一个诚实的负结果加一个被排除的假设——**在只有两轮预算的情况下，
   知道哪条路不通和知道哪条路通同样值钱**。
