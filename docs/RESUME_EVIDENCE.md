# 简历证据（R5 收口；holdout 观测次数以 `HOLDOUT_LEDGER.md` 为准）

本文件是简历与面试表述的**唯一取数口径**。规则来自 `docs/CAREER_CONTEXT.md`：
只写实际运行得到的数字；不写 SOTA；不把内部固定子集说成官方榜单；
不把单次成功演示说成生产稳定性；**项目可以输出 NO-GO，能拒绝不合格候选本身是工程价值**。

**本版最重要的变化**：项目的核心结论不再是"某个候选达标"，而是一个 2×3 实验矩阵，
它把**提示词工程**与**后训练**的贡献分离到了类别级。这是绝大多数同类项目给不出的证据形态。

LOG-20260814-01/02/03。

### 1.2b 核心结果二：跨规模验证推翻了"越多投影越好"（**dev 60 条，同一份新 prompt 数据**）

| 模型 | 零训练 base | attention-only | 全 linear layer |
|---|---|---|---|
| **Qwen3-4B** | 54/60（elig 9/10） | 55/60（elig 5/10） | **60/60**（elig 10/10） |
| **Qwen3-1.7B** | 44/60（elig **0/10**） | **58/60**（elig 10/10） | 45/60（elig 10/10） |

**1.7B 上方向完全相反**：attention-only 是强正作用（+14 条），全 linear 几乎无增益。
1.7B 全 linear 的 15 条失败**全部**是"该拒绝却没拒绝"（`refund_denied_ownership`
10/10 全灭），`policy_violation` 0→5，`average_tool_calls` 1.267→2.083——**学过头**，
被训练数据 2:1 的执行偏向带跑，丧失拒绝能力。

**结论：LoRA 容量必须与模型规模匹配，不存在"越大越好"。** 容量不足学不会条件决策，
容量过剩牺牲与主偏向相反的能力。出处：LOG-20260814-05。

### 1.6 延迟代价的归因（**这条最容易被讲错，务必按此口径**）

候选变慢**不是**因为"多做了工具调用"：

| 量 | base | 候选 | 比值 |
|---|---|---|---|
| average_tool_calls | 1.308 | 1.500 | 1.146 |
| average_turns | 2.042 | 2.167 | 1.061 |
| average_output_tokens | 92.2 | 131.7 | 1.429 |
| average_latency_ms | 1958 | 4457 | **2.276** |
| **单次调用耗时** | **1497 ms** | **2971 ms** | **1.985** |

调用次数只增加 14.6%，而单次调用耗时翻倍。差额来自**全 linear layer LoRA 的推理开销**
（7 个投影层每次前向多做一次低秩矩阵乘）。旁证：第一次观测用 attention-only adapter
（4 投影），p95 比值仅 **1.087**。

**因此 R4 的最终结论是一个真实的效果/延迟权衡**：LoRA 从 attention 扩到全部 linear layer
换来 task_success +14.2pp（120/120 满分、三项安全指标清零），代价是 p95 延迟接近翻倍，
发布门禁据此拒绝上线。

**三次观测均已消耗，封存 holdout 不再有"未观测"状态。**

**第三次观测（2026-08-15，R4.5 代码冻结后）**：任务指标与第二次**逐位相同**，
两套门禁口径都仍是 `NO-GO`。同时把候选的 LoRA 合并回基座后重测——同样 120/120、
调用次数一模一样，单次调用 2946.5 → **1717.7 ms**、p95 比值 2.0250 → **1.2141**。
**但那还不是发布判定**：当时的封存契约要求 candidate = 同一基座 + adapter，
合并版结构上无法作为候选（LOG-20260815-03）。

封存证据契约**——且做到不作废此前七份证据中的任何一份。这条链条里没有一步是
"换个更强的模型"。**然后又自己建了一个分布外集合，把刚拿到的 GO 打了一半**——
证明那 120/120 主要是模板内插值。能主动产出推翻自己结果的证据，比那个 GO 更值钱。

### 1.7 独立重建复验：SPEC §6 第 6 条已做掉，代价是一个新的边界

> 完整记录见 [`REBUILD_VERIFICATION.md`](./REBUILD_VERIFICATION.md)。

同一份 SFT 配置、同一份训练数据、同一个基座、同一组超参，只换 `--seed` 重训两次，
再在同一份 base 证据（`base-002`，54/60）上做配对评测：

| 运行 | seed | dev task_success | 政策违规 | 非法调用 |
|---|---|---|---|---|
| `base-002`（零训练） | — | 0.9000（54/60） | 5 | 0 |
| 原候选 `sft-006` | 0 | 1.0000（**60/60**） | **0** | 0 |
| **重建 A** | **0（同 seed）** | 0.9667（**58/60**） | **0** | 0 |
| **重建 B** | 1 | 1.0000（**60/60**） | **0** | 0 |

**第 6 条门禁满足**：两次独立重建都高于零训练基座（三次运行的最低值 58/60 仍高于 54/60），
政策违规在三次训练运行里**都是 0**。正向提升不是 seed 彩票。
**不写"显著高于"**——n=3 给不出置信区间。

**但同时暴露了一件此前不知道的事**：**同 seed 重跑产出的权重逐位不同**
（`8a49251f…` / `c93c6698…`），且这是在**训练代码自 2026-08-09 起零改动、数据哈希
一致、解析后配置只差两行输出路径**的前提下发生的——是 GPU 非确定性归约，不是缺陷。
后果是：**"60/60"不是一个常数，它有 ±2 的运行间波动**，而波动**全部**落在
`refund_recovery` 这一个类别上（10/10 → 8/10 → 10/10），正是"后训练独占贡献"的那一类。

**面试口径**：这一条比"复验通过"本身更值钱——我做这次复验是为了让一个满分数字站得住，
结果发现那个满分数字本身在满分附近抖动。所以我把 dev 的表述从"60/60"改成
"**58–60/60，三次同配置运行**"。

> **面试官很可能第一反应是不信这些数**。逐个数字的机制、它旁边不好看的那一半、
> 以及它不能支持什么，见 [`READING_THE_NUMBERS.md`](./READING_THE_NUMBERS.md)。

### 1.8 泛化修复（R6）：**这是项目最强的一条**，也自带账单

> 完整记录见 [`GENERALIZATION_FIX.md`](./GENERALIZATION_FIX.md)。

**诊断**：把分布外失败按子类拆开，发现训练把零训练基座**本来会做**的两类打没了
（`code_switch` 1.0→0.0、`colloquial` 0.5→0.0），失败全部是 `premature_final_response`。
机制是 240 条 train 全来自 12 句「请核实…」的书面祈使句模板——模型学的是
**表面形式 → 动作**，不是**语义 → 动作**。

**干预**：LLM 措辞池（267 条，$0.0061）做训练增强，**只改 user 的第一句话**，
工具调用与目标状态一个字不动。措辞按 `sha256(措辞+固定盐)` **确定性三分**，
训练用的与评测用的**逐条互斥**。

**封存分片（只观测一次，代码冻结后跑，运行内容事先固定）**：

| | 总计 | `eligible` | `recovery` | 三个拒绝类 | 政策违规 |
|---|---|---|---|---|---|
| 零训练基座 | 0.7167 | 0.30 | 1.00 | 0.60/0.90/0.80 | 3 |
| 旧候选 `sft-006` | 0.7333 | **0.10** | **0.30** | 1.00 ×3 | 0 |
| **新候选 `sft-008`** | **1.0000** | 1.00 | 1.00 | 1.00 ×3 | **0** |

**独立迁移检查**（作者手写的 OOD v1，生成过程完全不同，**从未用于选择**）：
`expression_ood` **0.00 → 1.00**（五个子类全满分），总分 0.5833 → **0.8667**。

**账单（必须与收益一起说）**：模型变得更倾向执行，于是「不该动手时也动手」——
dev 上新增 **2 次政策违规**（`refund_denied_window`），OOD v1 的 `scenario_ood`
0.75 → **0.60**（`partial_refund` 1.00 → **0.00**）。两个只差 oversample 的候选
出现**完全相同**的 dev 失败签名，因此这个代价可确定地归给措辞增强本身。

**面试口径**：这一条把项目从「我发现了一个问题」推进到「我诊断了机制、做了干预、
在一个只观测一次的分片上验证、并在一个我从未用来选择的独立集合上确认了迁移，
同时把代价量化到了具体类别」。**收益与代价来自同一个改动，这是最难伪造的形状。**

| "模型泛化了"（R6 之后） | 只能说「对**同一个生成器**产出的、训练从未见过的措辞更鲁棒了」。措辞池由单一 provider、单一 prompt 生成；**对任意真实用户输入的鲁棒性没有被测量** |
| 只写 R6 的收益不写代价 | 收益（`eligible` 0.10→1.00）与代价（dev 新增 2 次政策违规、`partial_refund` 1.00→0.00）**来自同一个改动**，两处同一机制。只报一半是误导 |
| "R6 候选通过了发布门禁" | **本轮没有消耗第五次封存 holdout 观测**。`sft-008` 从未进入任何 release 判定，四次观测的结论一条未改 |
| "120/120 证明模型可靠" | `ci95` [1.0,1.0] 是满分的退化区间；任务集为 2 工具 / 6 类 / 单一中文零售退款场景，每类 20 条 |
| "dev 60/60 证明模型能力" | 每类 n=10，且 **dev 已被用于从 4 个候选中选出这一个**，存在选择偏差，holdout 必然回落 |
| "dev 是 60/60" | 三次同配置运行是 **60 / 58 / 60**（§1.7）。写单点 60/60 而不写区间，等于把一次运气好的运行当成常数 |
| "训练结果可以逐位复现" | **已被自己的实验否定**：同 seed 重跑产出逐位不同的权重。本项目在 bundle/manifest/qualification 链路上都能逐字节复现，**训练是唯一的例外** |
| "CI95 显示显著改善" | 60/60 的 `task_success_ci95` 是 [1.0,1.0]，那是满分的退化区间，不是显著性证据 |
| "达到 SOTA / 超过 GPT-x" | 无跨模型对比，内部固定子集不是公开榜单 |
| "生产可用 / 稳定服务" | 单次演示，无压测、无长稳、无多租户 |
| "LoRA 投影挂得越多越好" / "容量决定训练符号" | 只在 4B 成立；1.7B 上 attention-only 反而最好，全 linear 让拒绝类由 30/30 崩到 15/30 |
| 把 4B 的 prompt/训练分工结论当跨规模规律 | prompt 对 1.7B 完全无效（elig 0/10）；分工结论是**模型规模依赖**的 |
| "1.7B 的 58/60 优于 4B 的 55/60" | 不同基座不可直接相比；跨规模只比"训练相对同规模零训练 base 的符号与量级" |
| "prompt 工程无用" 或 "SFT 无用" | 两者都被数据否定：prompt 独占 `refund_eligible` 的 +4，训练独占 `refund_recovery` 的 +5 |
| "延迟数可跨运行比较" | 共享 GPU，各次运行他人占用 0%–98% 不等，`train_runtime` 223 s 与 294 s 之差属占用差异 |
| "泛化到多领域" | 2 工具 / 6 类 / 单一中文零售退款场景；跨模型规模未验证 |
| "定位根因为训练数据动作长度失衡" | **该假设已被自己的实验证伪**（§1.4 第一行） |
| BFCL 相关成绩 | 属 legacy 轨道，与主线无关，163/200 与 167/200 只能表述为项目固定单轮 AST 子集结果且不得声称稳定提升 |

## 3. 简历 bullet（已定稿）

两版都只用 §1 的数字。**默认用方案 B**；投 Agent 平台 / 评测基础设施类岗位时换方案 A。
两版都以「拿到 GO」开头再给边界——**不是因为 GO 好看，而是因为一个只会输出 NO-GO 的
系统证明不了门禁是有效的，而不是过严的**。

### 方案 A —— 面向 Agent 平台 / Agent Evaluation / 系统开发岗

> **RetailAgentOps｜零售工具 Agent 的单卡适配与发布流水线**（个人项目，Python/PyTorch/FastAPI）
> - 设计并实现 `build / evaluate / release / serve` 四接口流水线，覆盖轨迹数据执行式质检、
>   冻结任务配对评测、版本化发布门禁与单卡服务；**936** 项测试、Ruff/mypy/依赖锁/公开发布
>   审计全绿，一条命令可在纯 CPU 环境复现全链路并断言内容哈希等于冻结期望值。
> - 建立**不可伪造的证据链**：运行报告以全字段自哈希为 ID、逐产物 SHA-256 绑定、
>   配对比较前强制校验模型/生成参数/数据/commit/依赖锁/prompt 哈希同条件，任一字段被改动
>   即加载失败；封存 holdout 用两段式授权与五维指纹隔离，整个开发期只观测 **4 次**。
> - 用真实候选跑通**四次**发布判定：前三次输出 **NO-GO** 并驱动服务回滚到冻结基座
>   （`adapter_loaded=false` 可在 `/health` 核对）。其中一次候选在 120 条封存任务上达
>   **120/120**、成功率 **+14.2pp**、政策违规与非法调用清零，仍因 **p95 延迟比值 1.88 > 1.25**
>   被拒——**阈值一字未改，有测试锁定其与上一版逐字段相同**。
> - 把失败**精确归因到部署形态而非模型**：单次调用耗时 ×1.985 而调用次数仅 ×1.146，
>   代价来自全 linear LoRA 的前向开销；把同一份权重合并进基座后 p95 比值降到 **1.13**，
>   拿到项目第一个 **GO**，并通过 SPEC 的独立重建复验（换训练 seed 重训仍 58–60/60）。
>   为让"合并形态"能进配对判定，**版本化了封存证据契约**且七份旧证据的自哈希复算逐位不变。
> - 主动构造**分布外任务集推翻自己的结论**：同一候选掉到 **0.5833**、表达变化类 **0/20**
>   （比零训练基座差），证明 120/120 是模板内插值而非泛化；该读数被测试强制与 GO 成对出现。

**主语是系统与证据。** 适合"我们需要有人把 Agent 的评测与上线流程做扎实"的岗位。

### 方案 B —— 面向 Agent 后训练 / 算法工程岗（**默认**）

> **RetailAgentOps｜零售工具 Agent 的领域适配与失败归因**（个人项目，Python/PyTorch/PEFT）
> - 构建执行式训练数据流水线：商业 API teacher 采集 + replay/最终状态/政策 verifier
>   三重校验，240 条训练轨迹通过率 **99.2%**（正式批次 526 次请求 / $0.0559；另有一批 519 次 / $0.055 的先行采集暴露了一个环境缺陷，**两批合计约 $0.111**）；train/dev/holdout
>   五维指纹隔离防派生泄漏。单卡 Qwen3-4B QLoRA-SFT（4-bit NF4，r=16，3 epoch，
>   发布候选 `sft-006` **293.7 s**、峰值 **5.65 GB**、adapter **66,127,776 B**），评测推理峰值显存 **3.0 GB**。
> - **以 2×3 配对实验分离提示词工程与后训练的贡献**（2 种 prompt × 3 档 LoRA 容量，六次运行、
>   每格 60 条冻结任务）：一句显式授权指令使零训练基座的目标类别 **5/10 → 9/10**，
>   而"失败后重试"类**零变化**；后训练则把重试类 **5/10 → 10/10**、政策违规 **5 → 0**。
>   两者修的是不同失败，几乎不重叠。
> - **量化出 LoRA 容量与模型规模的匹配关系**：4B 上仅挂 attention 投影时 SFT 对目标类别
>   是净负作用，加上 MLP 三投影后同一份数据、同一组超参从负作用变为 **10/10**；但在
>   1.7B 上**方向相反**——attention-only 反而是强正作用（44/60→**58/60**），全 linear
>   因容量过剩被训练数据 2:1 的执行偏向带跑，拒绝类由 30/30 崩到 **15/30**。
>   **结论是容量必须与规模匹配，且数据配比与容量耦合、不是两个独立旋钮。**
> - 在 120 条封存 holdout 上做到 **120/120**（成功率 **+14.2pp**，政策违规 11→0、
>   非法调用 5→0），最终取得 **GO**；但该 GO 归因于**部署形态**——未合并形态对同一 base
>   重算仍 FAIL（p95 比值 1.92）。**已量化出容量的推理代价**：单次工具调用 1497→2971 ms，
>   而调用次数仅 +14.6%。
> - **主动构造分布外集合推翻自己的结果**：同一候选掉到 **0.5833**、表达变化类 **0/20**、
>   比零训练基座还差——这次 SFT 是**用表面形式鲁棒性换来了任务结构与安全性**。
>   全程被自己的实验推翻**五个**判断（含"根因是数据分布失衡""容量决定训练效果的符号"
>   "候选慢是因为多做了调用""训练可逐位复现"），据此确立"最终状态与政策 verifier 是
>   唯一主判据"——`verifier_reward` 已四次与主判据背离。

**主语是模型与归因。** 适合"我们需要有人把领域模型调出来并解释清楚为什么"的岗位。

### 共用的一句话总结（自我介绍开场可用）

> 我做了一条零售工具 Agent 的单卡适配与发布流水线。最有意思的结论不是模型变好了多少，
> 而是我用一组配对实验把"提示词工程"和"后训练"的功劳分开了——一句提示词就解决了
> 大半的"不敢执行"问题，而"失败后重试"只能靠训练；并且发现 LoRA 只挂 attention 时
> 微调对这个能力其实是**负作用**——但换到 1.7B 上这个结论就反过来了，所以真正的规律是
> 容量得跟模型规模匹配。最终候选在封存测试集上做到 120/120 并拿到了发布门禁的 GO，
> 但我又自己建了一个分布外集合把它打掉了一半——换个说法的请求上只有 0.58。
> 然后我把机制诊断出来了：训练数据的 12 句请求模板全是书面祈使句，模型学的是
> "出现这种措辞就调工具"。用 LLM 生成的措辞做训练增强之后，在一个**只观测一次**的
> 封存分片上做到满分，在一个我从未用来选候选的独立集合上"换个说法"那一类从 0 涨到满分。
> **代价我也算清楚了**：模型变得更爱动手，该拒绝的场景反而多错了两次。
> **我认为能拿出推翻自己结果的证据、并且说得清自己修好的东西代价在哪，
> 比拿出一个没人敢信的提升更有价值。**

## 4. 面试主动交代的五件事

不等对方问，主动说，可信度更高（细节见 `DEMO.md` §4、`INTERVIEW_PREP.md` §3）：

1. **那个 GO 是部署形态换来的，不是模型变强了** —— 四次判定里前三次都是 NO-GO。
   最难的一次候选在封存集上是 120/120、成功率 +14.2pp，只输在 p95 延迟比值 1.88 > 1.25。
   我没有改阈值（有测试锁定它与上一版逐字段相同），改的是**加载方式**：把 LoRA 合并进
   基座后，同一份权重、同一套行为、调用次数一模一样，比值降到 1.13 才拿到 GO。
   **未合并形态对同一份 base 重算仍是 1.92 FAIL。**
2. **120/120 不是泛化，而且是我自己测出来的** —— 分布外集合上同一候选 0.5833，
   表达变化一类 **0/20**、比零训练基座还差。冻结 holdout 与训练集共用同一批请求模板。
3. **"60/60"不是一个常数** —— 独立重建复验时发现同 seed 重跑产出逐位不同的权重
   （训练代码零改动、数据哈希一致），三次同配置运行是 60 / 58 / 60，
   波动全部落在 `refund_recovery` 这一个类别上。
4. **有一个环境缺陷是真实 API 采集才暴露的** —— `refund_denied_window` 场景的判定依据
   `current_day` 从未暴露给模型，任何推理式 Agent 都无解；CPU 测试全走 Oracle 所以没发现。
   真实采集通过率 30% 才暴露，修复后 95%。
5. **我的判断被自己的实验推翻了五次**（§1.4）—— 最值得讲的是"这个 delta 是训练挣来的"
   那一次：我一度可以用"候选比基座高 20pp"来写简历，是我自己去测了"给基座也换上那句
   提示词"，才发现那 20pp 里有一半是免费的、跟训练无关。**如果不做那次对照，这个数字
   放到简历上就是虚的**，而面试官只要问一句"你的基座用什么提示词"就会露。
